# Mapy (Tiled) — stan i reguły autorskie

> **Reguły dla KODU wczytującego mapy** → `src/world/CLAUDE.md`.
> **Reguły dla GENERATORÓW** → `tools/CLAUDE.md`. Tutaj jest to, co na mapach
> faktycznie stoi i dlaczego.

The starting location is `public/assets/maps/forrest.tmj` — a **160x60**
(5120x1920px) forest with a river, a ford, a road spine and a trader's glade in
the NE, wired as `MAPS.forest` and loaded by BootScene/GameScene. ⚠ **Resized
100→160 east-only on 2026-08-28** (`PROJECT_CHECKPOINT_RESIZE160.md`) — columns
x100–159 are structurally in place but painted blank, pending the terrain pass
for the new A9/Brzeg Północny and A10/Źródło zones. It is
**generated by `tools/build_mapa.py`**, not painted by hand; the script prints a
report and writes nothing unless given `--zapisz`, because once the map has been
touched in Tiled the `.tmj` is the source of truth and re-running would erase
that work. A second identical copy lives at `public/assets/forrest.tmj` (same
content, different relative PNG path, so it opens in Tiled from where it sits);
the game reads the one under `maps/`. `forrest.json` + its `.bak*` files are a
superseded export from the old tilesets — nothing reads them.

**Two sheets, two tilesets.** `Teren.png` carries the surfaces you walk on
(grass, dirt, sand, stone, water plus blob-47 transition sets) and `Nature.png`
carries the props that stand on them (tufts, bushes, trees). The split is
practical, not aesthetic: one blob-47 set is 47 tiles and the terrain keeps
growing, so sharing a sheet would renumber the trees on every terrain addition.
`TILESET_TEXTURES` in `TiledMap` maps a tileset's NAME inside the Tiled file to
the texture key we loaded it under — `Teren`, `Nature`, `Buildings`, `Kuznia`,
plus `Pole`/`pole_tileset` (crops, painted by the village's `pola`/`uprawy`
layers — see the note below). Three things follow, all of which have already
bitten once:
- **The name is the join, not the image path.** Rename a tileset in Tiled and
  its tiles stop drawing until this table is updated.
- **An unknown or unloaded tileset is skipped, not fatal** — the map still
  builds, minus those tiles, with a console warning. Only
  `MAPS.requiredTilesetName` ("Teren") is mandatory: a map missing its props is
  a bare field you can still walk around, a map missing its ground is nothing.
- **Collision is keyed `tilesetName#localId`, not by local id alone.** The name
  is what lets duplicate embeds of one sheet share their shapes; but with two
  DIFFERENT sheets, plain local ids collide outright (Teren's tile 16 and
  Nature's tile 16 are different pictures) and a tree's collision box would
  silently start blocking a doorway.

**`pole_tileset.png` (crops) was registered ahead of any map using it, and now
has its first real use.** `tools/build_pole.py` produced it for a while before
anything loaded it, so painting the three-field rotation from
`docs/wioska_plan.md` §4.5 would have ended in an evening's work rendering as
nothing but a console warning — the second bullet above, in its worst form.
Measured, not assumed: 461×395, **14 columns × 12 rows, 32px tiles on a 33px
pitch**, 163 of 168 cells filled, gap columns verified fully transparent.
Registered under BOTH `Pole` and `pole_tileset`, because Tiled names a new
tileset after its image file and a name mismatch is the same silent failure —
the same reason `NPC_OBJECT_NAMES` takes English and Polish spellings.
**As of E1 (2026-08-10) `village-zagaje.tmj` actually paints it**: a new
`pola` tile layer (inserted before `buildings` in draw order, same reasoning
as `path`/`undergrowth`), tileset firstgid 571 (right after Kuznia's
514+57).
- **All three niwy of the three-field rotation are now painted (E1 closed,
  2026-08-11)**: **północna** (fallow, x18-46/y27-36), **południowa** (rye,
  x18-46/y77-86, west of the road) and **wschodnia** (oats/barley alternating
  with flowering flax, x66-78/y70-86). ~595 soil + ~492 crop tiles.
- ⚠ **The fallow is painted to a DIFFERENT rule than the other two, and that
  difference is the whole point of a three-field rotation.** It keeps the same
  structure (horizontal zagony, 2–3 rows) but only ~48% coverage: some bands
  ploughed, some stubble, some greening over, some left as bare grass where
  Gniewko's sheep graze (`wioska_plan.md` §4.5/§5.9). Painted as densely as
  the rye it would stop being fallow, and three identical fields show three
  fields, not a rotation. It started as 20 token tiles, which read as a symbol
  next to two full fields once those existed.
  - Its palette avoids the second layer almost entirely: `ugor_bruzdy_pion_*`
    (id18/20/21) and **`pedy_kielki_*` (id25-28)** are both `grunt` at 1.00
    coverage — the latter is soil with green shoots, exactly "resting land
    growing over". Only the stubble (`sciernisko_sloma_*`) is `nakladka` and
    needs soil under it.
  - **Meadow herbs are left standing in its gaps on purpose.** `HERBS[*].
    siedlisko` puts rumianek and krwawnik in open sun — a fallow is their
    *correct* habitat, unlike the rye field a krwawnik had to be moved out of.
    The generator skips a 1-tile radius around each stanowisko, and because
    the fallow is patchy anyway the gap doesn't read as a hole.
  - **It takes TWO layers, and that is forced, not stylistic.** Of 13 grain
    tiles only 3 are `rola: grunt`; of flax and `nac`, **none**. Painting the
    crop on one layer would mean either three tiles for a whole field
    (visibly repeating) or holes in it. So `pola` carries the SOIL
    (`grunt`+`czysty` tiles) and a new `uprawy` layer carries the CROP
    (`nakladka`), showing the furrows through its gaps — the same split
    `buildings`/`buildings-detale` already uses. `TiledMap` handles layers
    generically (`-over` is the only special case), so this needed no code
    change.
  - **Strips run PERPENDICULAR to the road** (`wioska_plan.md` §4.5) — the
    main road is vertical at x50-51, so the zagony are horizontal bands 2–3
    rows tall. ⚠ **Adjacent bands must never share a crop variant**: there is
    no baulk tile between zagony, so the variant change is the *only* thing
    drawing the boundary — two identical bands merge and the striped reading
    disappears.
  - **Root crops are excluded on purpose.** Of the 17 tiles `build_pole.py`
    cut in half (bottom in the sheet, top in a loose `pole_over_NN.png`),
    **16 are `korzeniowe`** — the odd one out is `pedy_mlode_5`. Without a
    working `-over` layer they'd render topless. Grain and flax are whole,
    which is why the other two niwy could be painted now, and it is also why
    B6 (vegetable beds) is a *placement* job rather than an art one: cabbage
    (12 tiles, 3 growth stages) and `nac` (29) are all complete. See
    `polowka` in `docs/pole.json`.
  - A yarrow (`krwawnik`) stanowisko sat inside the eastern niwa. Cutting the
    field around it left a 5×5 clearing that read as a glade — the fix was to
    **move the stanowisko** to open meadow just east (74,82 → 80,74), since a
    niwa is authored content while stanowiska are deliberately more numerous
    than the plants standing on them (`GATHER.activeRatio`).
- **It now HAS a semantic catalog** — `docs/pole.json`, written by
`tools/katalog_pole.py` (2026-08-10), closing the last sheet that had
none. The split is deliberate: **measured on every run** — opaque
bounding box, coverage, colour shares, and `trawa` (which edges meet
turf, i.e. whether a tile is an edge tile of the strip); **read off the
sheet once** — crop species, growth stage, and furrow direction.
Automatic furrow detection was tried and rejected: row variance latches
onto the grass band (transition tiles scored as the most "furrowed" on
the sheet) and frequency analysis latches onto the rhythm of the PLANTS
(top scorers were cabbage and turnip, not ploughed earth).
- **The sheet mixes GROUND tiles with bare PLANT sprites on transparency**,
  because tiles are cut by connected-component labelling — a "tile" is
  however much joined into one component. Coverage runs continuously from
  0.12 to 1.00, so the catalog tags each tile `rola`: **`grunt`**
  (coverage ≥ 0.95, **68 tiles**) covers its own cell and may be laid as
  solid field; **`nakladka`** (95) needs soil underneath.
- ⚠ **`_dopelnij_krawedzie` in `build_pole.py` is what makes this sheet
  safe to hand-paint in Tiled — don't remove it.** Each tile is scaled by
  a uniform factor, then centred horizontally and bottom-aligned, so
  `round(w * skala)` lands on 29–31px instead of 32 and leaves 1–3px of
  transparency at an edge. On the map that is **a hairline gap showing the
  grass underneath** — reported as exactly that ("kafelki działek nie
  pasują"). Extending the edge pixels into that margin took fully-covering
  tiles **11 → 56** and `grunt` **38 → 68**, with zero change to any
  original pixel (verified against a pre-change copy).
  - **Going by the opaque bounding box does not work.** A *partially*
    transparent edge column is the common case: id6 had 28 of 32 pixels
    empty in column 0, so `xs.min()` was 0, the bbox test never fired, and
    the seam survived down 7/8 of the tile. Copy from the immediate
    neighbour instead.
  - ⚠ **The "is this even ground?" gate is mandatory.** The tempting and
    **false** assumption is that copying from a neighbour is self-limiting
    because a plant's margin has a transparent neighbour too — true only
    until a plant touches the tile edge, and several do. Without the gate,
    id90 grew a horizontal smear pulled out of its flower to the right
    edge and id147 a green bar down its whole left side. Both are obvious
    on a before/after render and invisible in any numeric report.
  - The split is clean, not arbitrary: a ground tile's central 16×16 block
    is 0.99–1.00 opaque, every plant is at most 0.78 (densest `nac` 0.78,
    a seedling 0.32) — an empty gap between the groups, so the 0.99
    threshold isn't balanced on anyone's edge. Margins wider than 3px are
    deliberately left alone: that's real shape, not rounding.
- ⚠ **An edge STRIP alone does not identify an edge tile — check the
  CORNERS too.** A tuft of turf sitting in one corner is a dozen-odd
  pixels out of a ~124px edge strip, about 0.15, under the 0.25 edge
  threshold. So **id6** (green block in its bottom-right) and **id11**
  (same, bottom-left) — a matched pair of *corner* tiles — were catalogued
  as clean `ugor`, i.e. as field interior, and one of them got painted
  into the middle of Zagaje's strip where it read as a tuft of grass
  growing in the field. Spotted by the user from a screenshot; no number
  in the report showed it. The catalog now measures corners separately
  (10×10 block, threshold 0.12) and carries `naroznik`.
- **For a field interior, use only tiles with `czysty: true`** (not one
  green pixel anywhere). There are exactly **four** on the whole sheet:
  `ugor_bruzdy_pion_2/4/5` (id18/20/21, vertical furrows) and
  `ugor_bruzdy_poz_2` (id2, horizontal). `katalog_pole.py` prints that
  list at the top of its report. Zagaje's strips are painted from the
  three vertical ones, mixed so a single repeated tile doesn't reveal the
  grid. The two niwy from §4.5 (south:
żyto, east: jarzyna/len) are still unpainted.
- ⚠ **The `-over` half does NOT work yet, and cannot without new asset work.**
  `build_pole.py` writes the tall plants' upper halves as **17 loose
  `pole_over_NN.png` files of natural size** (8–24px tall, some 33–35px wide,
  i.e. wider than a tile) rather than a sheet. Phaser binds one image per
  tileset, so a Tiled "collection of images" cannot be bound here at all.
  Tall grain therefore cannot be walked behind until those are packed into
  their own 33px-pitch sheet **and** their ground-tile pairing (`pary` in the
  generator) is exported as a catalog, the way `docs/budynki.json` does it.
  Low crops (ploughed earth, cabbage, roots) need none of that and work today.

Both sheets are 640px wide while 19 columns at a 33px pitch occupy 626, so
Phaser logs `Image tile area not tile size multiple` for each. It is a warning,
not a fault — verified in-engine that the geometry still resolves exactly
(Teren 19x12 = 228 tiles, Nature 19x7 = 133, on the 33px pitch).

**A fourth tileset, `Kuznia.png` (forge/smithy equipment — piec, kowadło,
oselka, stojaki…), is embedded the same way**, bound at
`FIRST_KUZNIA = 495` (= `FIRST_BUILDINGS` + Buildings' 7 rows × 19 cols,
`tools/build_mapa.py`) and painted onto its own **`wyposazenie`** tile
layer — a normal-depth layer (not `-over`) sitting right after
`buildings-detale` in draw order, so equipment draws on top of the ground
but BEFORE `trees-base`, or a tree planted nearby would draw over the
anvil. The equipment catalog itself (`KUZNIA_WYPOSAZENIE`, a hand-authored
list of `(nazwa, dx, dy)` offsets — not a modular wall/roof kit like
`kafle_domu`, just flat props stamped onto open ground, because the
building kit has no real "interior": every `sciana` row is a solid
wall-textured block, `otwarty` only ever opens the LAST row, so there is no
way to get genuine walkable floor depth inside one) lives in
`build_mapa.py` but is **shared** — `build_wioska.py` imports it as
`M.KUZNIA_WYPOSAZENIE` rather than keeping its own copy, since the layout
logic (why the bellows touches the forge, why the grinding corner sits away
from the fire) has nothing to do with which map hosts it. Whichever map
places the yard must manually OR its footprint into `budynki_kafle`/
`zakazy` (with a 1-tile buffer) so trees don't spawn on top of it — that
does NOT happen automatically for hand-placed tiles the way it does for
`BUDYNKI_NA_MAPIE` entries.

**The kowal (blacksmith) lives in the VILLAGE, not the forest.** He was
first placed beside the Hunter's cabin on the forest's NE glade — reported
immediately as backwards: a hammering, smoking forge next to the Hunter's
hunting ground would scare off every animal he's meant to hunt, and
`docs/swiat.md` already said the smith's place is in the village anyway.
He now stands in his own plank-and-thatch shed in `village-zagaje.tmj`
(`BUDYNKI_WIOSKI` → `"kuznia"`, west of the plaza), with the same equipment
yard in front of its door. **Each named NPC now spawns on exactly the map
that authors its point — no more fallback.** `GameScene.create()` used to
spawn the Hunter AND the Blacksmith unconditionally on every map, falling
back to a procedural or fixed-offset position when a map didn't author one
— which is exactly the mechanism that put the forge next to the Hunter in
the first place. Fixed: `if (map.merchantSpawn) this.addNpc(...)` /
`if (map.blacksmithSpawn) this.addNpc(...)`, so the forest (which authors
only `"merchant"`) shows only the Hunter, and the village (which authors
only `"blacksmith"`) shows only the Kowal. Verified in-engine on both maps
(`window.game`, manual `game.loop.step()` since a hidden Browser pane won't
composite frames for a screenshot) — exactly one `Merchant`-class NPC per
map, at the authored coordinates, no console warnings.

**The current map has NO collision at all** — zero static bodies, the whole
world is walkable (verified in-engine). That is a deliberate staging decision,
not an oversight: layout first, collision once the layout settles. Both
authoring routes still work when it's time — a shape in Tiled's Tile Collision
Editor, or a boolean `solid` tile property.

**Layers, one per kind of thing.** Everything green on one layer is
unmaintainable: fixing a single tree in a thicket would mean cutting it out
from under the grass tufts.

| layer | contents | sheet |
|---|---|---|
| `ground` | grass, variants mixed | Teren |
| `water` | river + backwater (blob 47) | Teren |
| `sand` | the ford's shoal (blob 47) | Teren |
| `path` | roads (blob 47) | Teren |
| `undergrowth` | grass tufts | Nature |
| `bushes` | bushes | Nature |
| `pola` | field SOIL — village only, `grunt`+`czysty` tiles | Pole |
| `uprawy` | the CROP standing on it — village only, `nakladka` tiles | Pole |
| `buildings` | building walls | Buildings |
| `buildings-detale` | doors, windows (overlays onto the wall) | Buildings |
| `znaki` | gate scenery — signpost, fence gap at a map gate | Znaki + Buildings |
| `trees-base` | the BOTTOM row of every tree | Nature |
| `trees-over` | everything above it — drawn ABOVE entities | Nature |
| `buildings-over` | roofs — drawn ABOVE entities | Buildings |
| `objects` | spawns | — |

Splitting a prop across a base layer and an `-over` layer is the only way the
player can walk BEHIND it: a layer whose name ends in `-over` gets
`DEPTH.overhead`, everything else sits under the entities. The trunk tile has
to stay underneath, or the crown would cover a player standing *in front of*
the tree. When editing in Tiled, a whole-tree stamp lands on ONE layer — move
its bottom row to `trees-base` afterwards.

**Buildings split by a computed line, not by "bottom row".** `kafle_domu` in
`tools/build_mapa.py` decides which rows are roof (`buildings-over`) and which
are wall (`buildings`); the tree rule would be wrong here — a wall is two tiles
tall, so a player standing beside it would vanish behind their own house.
One building is placed today: the hunter's cabin in the NE glade (tile 64,3),
with the Hunter standing at its door. It deliberately keeps the **rectangular**
ridge roof (`styl="kalenica"`, the default): it has been on the map from the
start and switching it to the `/\` roof would change its height, while the
distances around it to the campfire, the blacksmith and the spawns are already
measured and asserted. New village buildings use `styl="szczyt"` plus
`material="deski"`, `wrota`/`drzwi_pol`/`klapa`/`otwor_siana`/`otwarty=(od,do)`
— barn, cowshed, chicken coop and stable are descriptions, not new art.

**A map with no object layer loses its whole roster, silently.** Without a
`player` object the spawn is found by scanning open ground, and with no object
layer at all the enemy list falls back to `defaultEnemySpawns` — three rabbits.
Re-exporting from Tiled without the object layer therefore looks like "the map
works, the game is empty". Check the layer survived the export before debugging
anything else.

**An empty enemy list is NOT that failure, and telling the two apart needs
`hasObjectLayer`.** "This map has no enemies on purpose" and "this map's object
layer vanished" both arrive as an empty `enemySpawns`, and the fallback above is
written only for the second. `TiledMap` therefore reports whether any object
came through at all; a map that authored objects clearly exported its layer, so
GameScene honours zero enemies as a decision. **This was a real bug**: the
village authors no enemies, so the safety net fired and scattered three rabbits
around Zagaje's own `player` point — which, once that point moved to the plaza,
put wild animals outside the Sołtys's door. A map wanting enemies still just
authors them; the code map (`MapBuilder`) has no object layer at all and keeps
its rabbits. Its
**object layer** carries the spawns as named point objects: one `player`, plus
`rabbit` / `boar` / `wolf` / `greywolf` (accepted as `szary` too) / `spider` /
`venomspider` (accepted as `skoczek` or `pajak_jadowity`) —
`TiledMap.readSpawns` maps those names to typed `EnemySpawn`s — plus any number
of `campfire` points, an optional `merchant` (also accepted as `hunter`) and a
`blacksmith` (`kowal`). Both NPCs fall back to procedural placement when
unauthored, so a map without them still works.

**Spawn distances are load-bearing, not decorative, and `build_mapa.py` checks
them on every run** (prints OK/BLAD per rule, so a hand edit that breaks one is
caught by re-running the report):
- The three pack wolves sit **115 / 132 / 133px** apart, so any one of them
  links the whole trio through a single howl (`WOLF.pack.callRadius` = 200).
- The **Szary is 296px** from the nearest of them — outside that radius — which
  is the only thing stopping a pack howl from dragging a 190 HP elite into a
  three-wolf fight. The margin over 200 is deliberate: at 211px, nudging one
  wolf two tiles in Tiled would flip it.
- The **campfire is 119px from the Hunter**, which must exceed
  `MERCHANT.interactRange + CAMPFIRE.interactRange` (48 + 44 = 92). Two circles
  further apart than the sum of their radii cannot overlap, and that is what
  lets the shop and the fire share the `E` key without one press firing both.
  The **Kowal** is 128px from the Hunter (needs > 96 = two interact ranges) and
  161px from the fire.
- A **fourth, lone wolf sits 399px from the nearest pack member** (and 643px
  from the Szary) on the route from the player's glade to the south-west. It is
  a *trial run*: the pack is the game's first "you cannot fight this one at a
  time" encounter, and until this existed the only way to find out whether you
  could take a single wolf was to meet three. Twice the `callRadius`, so
  neither howl reaches the other — that separation is the whole mechanic and
  300px is asserted as the floor. `raport()` tells the two apart by x
  (the pack has the three smallest), so keep that ordering if you move them.
- **Spiders are ≥340px from every boar, and that reverses an earlier decision.**
  Two of the three used to sit *inside* a boar's `aggroRange` (175) on purpose:
  the web made the boar's dodgeable charge undodgeable. The author's call
  (2026-08-13) is that a boar and a spider should be two encounters, not one.
  The threshold is `SPIDER.aggroRange` (230) plus room for the fight to drift,
  and the "one teaches, the pair shows what for" structure survives the move —
  the solo one is now simply the first on the route rather than the deepest.
- **Rabbits are ≥380px from every wolf-kin** (was 276px at the closest). The
  threshold is `WOLF.deAggroRange` (320) plus margin: a wolf pulled toward the
  player must never end up standing on a rabbit's patrol, or the pack fight
  acquires a third participant nobody invited.

The forest itself is a density field, not a scatter: an edge wall around the
whole map, a gradient toward the south-west (where the pack lives — that
darkening is the only warning the player gets before the first howl), and
large-scale noise for real thickets and real glades. Three layout bugs were
caught only by compositing the whole map to a PNG and looking at it, never by a
number: a ford that severed the river along the entire valley, a horizontal
road that cut a channel through the lake, and a forest that read as an orchard
because the density noise was too shallow. **Look at the map, don't just read
the report.**

Export from Tiled with: **JSON** format, **Tile Layer Format = CSV**
(base64/zlib yields a silently empty map — Phaser has no decompressor),
**Infinite off**, and **Embed Tileset** (external `.tsx` references are rejected
outright).

Two authoring rules that are easy to get wrong:
- **Flat terrain -> tile layers. Anything the player walks behind -> an `-over`
  layer.** A tile layer draws as one batch and cannot Y-sort per tile, so a tree
  crown painted onto an ordinary layer can never be walked behind.
- **Collision is flattened across layers**: for each cell the *topmost
  non-empty* tile decides passability. That's what makes a walkable bridge over
  solid water work without special cases. Note the consequence with `-over`
  layers — a crown tile painted over a solid trunk cell would make that cell
  passable again.

### The village map and map-to-map portals

A second map, **Zagaje** (`public/assets/maps/village-zagaje.tmj`, wired as
`MAPS.village`), sits **north of the forest** — reached by walking the
forest's road spine to its top edge. This is a **geographic reversal of
`docs/swiat.md`**'s original sketch (village south of the forest).
`docs/wioska_plan.md` §1.2d and §10 (decisions D-2/D-3) formally accept the
north layout as final and rebuild the mill/hunter/herbalist placement around
it — `swiat.md` §3 now carries an explicit callout pointing at that
resolution instead of describing its own ASCII layout as current. Generated
by `tools/build_wioska.py`, which **imports `tools/build_mapa.py`** for the
dimension-agnostic reusable pieces (`kafle_domu`, `wysokosc_budynku`, the
`BUDYNKI`/`ARKUSZ_B` catalogs, the tree-species catalog) and monkey-patches
`M.SZER`/`M.WYS`/`M.rng` before touching the pieces that are NOT
dimension-agnostic (`Warstwa`, `maluj_obszar`, `pusta_maska` — these read
`SZER`/`WYS` as globals of the `build_mapa` module, resolved at *call* time,
so reassigning them before the first call works and is safe because each
generator always runs as its own process). Tree placement is its own much
simpler routine (`zbierz_drzewa`) — a rare border scatter, not the forest's
density-field/gradient system, because a cleared village needs a treeline for
framing, not a forest.

Gniewko's cottage + open sheepfold**) plus a road, a small plaza, a
**well** (`src/entities/Well.ts`,
`studnia_zlozona.png`, collision on its circle — still the ONLY collision

2026-08-11 because it had been standing on the road's own centre line
x50-51 — a well belongs beside the through route, not in it) and a short fence (`zagroda_*`, the existing paddock
rail — explicitly a "threshold marker", not a wall) near the gate. Five more
villagers stand as **talk-only presence** — Sołtys/Dobiesław, Rolnik/Dobek,

**Engine side:** `TiledMap.ts` reads Tiled point objects named `"portal"`,
decoding Tiled's custom-properties array (`[{name,type,value}, …]`, copied
through unchanged by Phaser's parser — see `readProps`) into a `target` map id
plus a `spawnX`/`spawnY` pair **in the target map's own pixel space**.
`GameScene` carries the crossing through `scene.restart({mapId, spawn, hp})`
— restart re-runs `init()`/`create()` on the same "Game" scene key, which is
why `MAP_BY_ID` maps a short id ("village") rather than a Phaser cache key:
the portal object shouldn't need to know how the target map's JSON was
loaded. Three things worth knowing if you touch this:
- **A portal is walk-through, not an interact prompt** (`PORTAL.triggerRadius`,
  update()) — a gate is geography, the way loot pickup already is, not an NPC
  needing `E`.
- ⚠ **THE PORTAL POLICY, in one sentence: a crossing is CONTINUOUS for the character; only the WORLD is rebuilt.** Established 2026-08-16 after an audit found the boundary had no policy at all — three kinds of state took three different paths and only one had been chosen on purpose. HP was carried deliberately (`pendingHp`); **ability cooldowns were being wiped**, i.e. a free reset for touching a gate, behind a wrong technical justification (see the Abilities entry); and **buff EFFECTS were silently dying while their ICONS lived on**, because the four buff fields (`damageBuff`/`slow`/`venom`/`foodHeal`) sit on `Player` — destroyed and rebuilt on restart — while the `Buffs` snapshot is module-level and `Buffs.clear()` hangs off UIScene's SHUTDOWN, which a portal never triggers. Net effect: eat a meal, cross a gate, and the icon counted down while no HP arrived; venom was cured for free; Okrzyk showed as active when it wasn't. Now `Player.captureCondition()`/`restoreCondition()` carry those four fields through `scene.restart`, and the **presence of `condition` in the scene data IS the signal** — only a portal supplies it, so a save load or a new game falls into the other branch and gets `Buffs.clear()` + `Abilities.reset()` (which also fixes a save load inheriting the previous character's buff icons). ⚠ Carrying the raw timestamps works **only because the clock is monotonic**; if that ever changes, `captureCondition` is the one place to rebase them. Don't add a fourth behaviour to this boundary without deciding which side of that sentence it belongs on.
- **HP is carried explicitly (`pendingHp`) and would otherwise be a free full
  heal.** `Player`'s constructor always seeds HP from `Progression.maxHp` —
  fine for the very first `create()` a session ever does, but portals are the
  first time `create()` re-runs *during play*, and skipping this would let a
  player heal by walking through any gate, undercutting the whole
  regen/food/potion economy the RESPAWN-cost design fought to protect (see
  that note lower in this file).
- **The arrival point on each side sits outside the OTHER side's trigger
  radius on purpose** (a few tiles past the gate, not on it) — landing inside
  your own return trigger would bounce you right back. Verified in-engine:
  a full forest→village→forest round trip lands at the exact authored pixel
  each time, HP unchanged (regen aside), with no scene/listener leaks across
  two restarts.
- **`tools/portale.py` defines exactly FOUR points and the maps must carry
  exactly those.** The village had picked up a fifth: a second `portal` object
  at (1646.36, 3151.82) — fractional coordinates, i.e. a copy dragged in Tiled
  at a non-integer zoom — 30px from the real gate, with the same `target` and
  the same arrival. Harmless in play (the trigger loop breaks on the first
  match) and exactly the drift that module exists to prevent, so it is gone.
  If a gate ever needs to be wider than one point, widen it **in
  `portale.py`**, on both maps at once; do not park a second object next to
  the first.
- ✅ **The gate now catches the WHOLE width of the road, and that had to be
  fixed the moment the gates became visible.** It used to be a known, accepted
  defect: `triggerRadius` 28 spans 56px across a two-tile (64px) road, so a
  player hugging the far edge walked past it. Tolerable while a gate was an
  invisible point — indistinguishable from "I wasn't there yet". **Once a
  signpost and an entrance marker stand on it, the same miss reads as a broken
  game**, so marking the gates and fixing the trigger are one change, not two.
  The fix is the one this file already predicted: **the gate sits on the road's
  centre line (the SEAM between two tiles), not in a tile centre** —
  `portale.py` grew `piksele_brama()` for exactly this, alongside the existing
  `piksele()` which still serves the arrival points. With `triggerRadius` 34 the
  forest gate covers x 1278–1346 against a road at 1280–1344, and the village
  gate 1598–1666 against 1600–1664. ⚠ Both numbers assume an EVEN road width;
  an odd one breaks the convention and the place to change it is `portale.py`,
  never one of the maps.
- ✅ **Every portal draws an entrance marker, and it is generated per portal
  rather than painted per map** (`PORTAL.marker`, `makePortalMarkerTexture`,
  `GameScene.addPortalMarkers`). A translucent arch-and-chevron laid flat on the
  ground, breathing between two alpha values, rotated to point the way out.
  - ⚠ **This is a VOCABULARY, and that is why it is not scenery.** A signpost
    marks a gate on a road and marks nothing at a cottage door or a cave mouth,
    so the player would have to learn a new sign per kind of place. One glyph,
    drawn identically on every transition there will ever be, is learned once.
    The signpost still exists — it makes the world look right — but it is not
    what teaches the player. (The idea is Margonem's transparent entrance icon;
    the register is already established here by the target-selection ring.)
  - **It costs nothing per new transition.** A transition cannot work without a
    `portal` object, so a marker derived from that object cannot be forgotten —
    a future door in a cottage is one point in Tiled and the marker appears by
    itself. A painted tile would be two jobs, one of them silent when skipped.
  - **Direction comes from the nearest map edge**, which is exactly right for a
    gate on a road running off the map (both of today's) and exactly wrong for
    the first door inland — hence the optional `dir` property
    (`up`/`down`/`left`/`right`) that overrides it. An unrecognised value falls
    back to the derivation rather than throwing: a typo in Tiled should cost a
    wrong arrow, not a map that won't load.
- ✅ **Gate scenery: a signpost at both gates, plus a fence gap in the forest**
  (`znaki` tile layer, inserted before `trees-base` so a tree crown still draws
  over it). This is the first thing to paint from **`znaki.png`**, registered as
  a fourth/sixth tileset (`Znaki`, firstgid 514 in the forest and 739 in the
  village) — appended at the END, which is the only safe place: inserting one
  would renumber every tile after it.
  - ⚠ **`wiata_slup_1` is NOT a free-standing post — it is 1024/1024 pixels
    opaque.** It is a wall-band piece of the open-fronted bay with the shed's
    dark interior baked in, so two of them beside a road render as two black
    holes in the grass. Same trap as the chimney tiles carrying their own
    background. The rail fence (`zagroda_*`, ~334/1024) is a real overlay and is
    what the forest gate uses: `zagroda_2` west and `zagroda_0` east, so the
    POSTS stand against the road and the rails run away from it.
  - ⚠ **The village gets the signpost and NO fence, deliberately.** Zagaje
    already has a fence running across the map at y95 with a gap exactly on the
    road — the gate has been framed there since the village was built. A second
    fence two tiles below it read as a leftover of the first.
  - Both findings came from **compositing the tiles to a PNG and looking at
    it**, not from any report — the same rule the forest layout already learned
    ("look at the map, don't just read the report").
