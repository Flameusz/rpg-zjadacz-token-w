# RPG Prototype

Top-down 2D action RPG prototype (WoW/LoL-style combat feel, pixel-art). Phaser 3 + TypeScript + Vite. Runs as a browser web app now; Capacitor/Android wrapping is future work — don't build for it yet.

## Status
Playable MVP is implemented and working. See the per-area checklist below before assuming something needs building — check the code first.

**`docs/swiat.md` is the world bible** — story, cast, village/forest layout, interiors and all narrative text, including a status table of which parts are already wired in. **`docs/wioska_plan.md` is the concrete village build plan** — a 30-resident roster (names, ages, households, sprite/interaction status), the measured layout, and the village economy, all read off the actual `.tmj` rather than off intent. Where the two disagree on village specifics (geography, headcounts, who lives where), `wioska_plan.md` wins — it records six decisions (D-1..D-6, its §10) that formally superseded `swiat.md`'s sketch, including the north-vs-south geography reversal noted below. `docs/prompt_wioska.md` is the meta-prompt that produced it, not content on its own — instructions for extending `wioska_plan.md`'s §5, never a source of game facts. `docs/ART_DIRECTION.md` is the visual style bible (measured cross-sheet palette overlap, pixel grid, per-sheet conventions) for every asset — creatures, buildings and NPCs alike. `docs/prompty_gemini.md` / `docs/prompt_sciany_gemini.md` log the Gemini image-generation prompts that worked (and why) for NPC portraits and wall tiles, so the next one doesn't start from a blank prompt. `docs/ZADANIE_drzewa.md` is a standing task brief for tree species art (5 of 9 species done). **`docs/odlozone.md` is the parking lot** — a flat, one-line-per-item list of things *consciously deferred with a reason and an unlock condition*, not the general ⏳ backlog (that's this checklist). Check it before a review so nothing parked gets silently forgotten, and before proposing work so nothing parked gets re-proposed without noticing why it was set aside. **`docs/dziennik.md` is the session diary** — a dated, reverse-chronological narrative of what happened each work session and why, newest entry first. Not a duplicate of this checklist (which describes current STATE, not history) — read it to catch up on a session's reasoning/arc without re-deriving it from the diff. Add a new dated entry at the top when a session wraps up with meaningful work done. This file (`AGENTS.md`) covers the CODE. Read `swiat.md` before writing anything player-facing (NPC lines, quest copy, place names) and `wioska_plan.md` before deciding WHERE in the village something stands or WHO lives there.

- **`window.dev` exposes the live core singletons** (Progression, Inventory, Equipment, Quests, Skills, Buffs, Abilities) in dev builds. Use it instead of `import()` from the console: a dynamic import gives you a SECOND module graph, so `Equipment.equip(...)` typed at the console mutates a copy nothing renders and every reading comes back stale. That cost real debugging time twice before the handle existed.
- `npm run dev` — dev server (also wired into `.Codex/launch.json` as `rpg-dev` for the Browser pane / `preview_start`)
- `npm run build` / `npx tsc --noEmit` — must both pass clean before calling any change done
- Verify visuals with `game.renderer.snapshot()` in the browser console, not `canvas.toDataURL()` directly — the WebGL backbuffer isn't preserved, so a plain `drawImage` grab comes back blank.

## Architecture
- `src/config/GameConfig.ts` — all tunable numbers (player/enemy stats, combat timing) + asset slicing constants. Change balance here, not in entity code.
- `src/core/Assets.ts` — loads the PNGs, builds procedural placeholders for anything missing (so the game always boots even with an empty `/public/assets`), slices the character sheet, extracts the sword/rabbit-face/NPC-portrait sub-textures and each item's icon — a real tile cut from `items.png` for weapons/armor, a colour-swatch placeholder for everything else (or for those same weapons/armor if `items.png` itself is missing).
- `src/core/Animations.ts`, `HitFlash.ts`, `EventBus.ts`, `InputState.ts` — small shared utilities. **`flashHit` takes a `restoreTint` option and it is not cosmetic** — see the enemy-telegraph note in the checklist below.
- `src/core/Interactables.ts` — **the one place that answers "what is the player standing next to".** Types only, no state: an `Interactable` carries a `kind` (`npc` / `campfire` / `gather`), a `key`, its own range and its position. `GameScene` keeps a single list and runs a single per-frame pass where **the nearest in-range one wins**, announcing changes through one `EVENT.interactableNearby`; `Merchant` and `Campfire` implement it, and every UI gates on the kind it cares about.
  - **This replaced a per-kind proximity loop, a per-kind event and a per-kind `keydown-E` binding.** Nothing stopped an NPC and a campfire being in range at once except *map geometry* — the fire is placed further from the Hunter than their two interact ranges combined, measured by hand and asserted in Python (`CAMPFIRE.spawnSearchRadii`). That guarantee is **pairwise**: every new kind must be re-measured against every existing one, on every map, and the failure is silent ("E does nothing" / "E does two things"). Herb gathering — dozens of hand-placed nodes per map — is what made it untenable.
  - **Deliberately NOT an `interact()` method.** The three kinds are answered in three different places and should stay there (a paused conversation window, a one-shot prompt, an instant pickup); one method would drag UI decisions into entity code. This answers "may I?", exactly like `Abilities` against `GameScene`.
  - Verified in-engine: sweeping 140 tiles of the forest's NE corner gives 7 tiles with only the NPC prompt, 6 with only the fire prompt, **0 with both** — and the widget states match the geometric counts exactly. Then, forcing the case the old code could not resolve (campfire moved to 40px from the Hunter, so both are always in range): nearer-Hunter → NPC prompt only, nearer-fire → fire prompt only, exact tie → registration order wins, **always exactly one prompt**. Cooking still works end to end through the new path (6 raw → 5 raw + 1 cooked at the fire; the same tap far away does nothing).
  - The old distance rule survives as a **placement preference** — a prompt that swaps as you shuffle between two things is still bad — but it is no longer what makes the key unambiguous.
  - ⚠ **`GameScene.removeInteractable` must NOT clear `nearby` before re-running the pass.** The change is announced by comparing the new winner against `nearby`, so clearing it first makes "nothing here now" compare equal to "nothing here before" — no event fires and the prompt stays on screen **forever**, until the player happens to walk into something else. Found in-engine, not by reading: gathering worked, the item arrived, and the bar just sat there over bare grass. Leaving the removed object in place for one comparison is also what correctly *keeps* the prompt up when another plant of the same species is still in range.
- `src/core/Gathering.ts` + `src/world/NodeSpawner.ts` + `src/entities/Gatherable.ts` + `src/ui/GatherPrompt.ts` — **herb gathering**: the first thing in this game the player can do to the world that isn't hitting it or talking to it. See the checklist entry below.
- `src/ui/WorldPrompt.ts` — the bottom-centre "press E to…" bar, shared by `CampfirePrompt` and `GatherPrompt`. Extracted when gathering became its third user: the position (`width/2, height − 70`) was already written out three times, and three copies of a screen coordinate is how two prompts end up 6px apart after somebody nudges one. `NpcDialog` still keeps its own — its prompt is entangled with the panel's lifecycle.
- `src/core/Progression.ts` — XP/levels/attributes singleton (melee damage range reads the equipped weapon via `Equipment`, falling back to `PLAYER.damageMin/Max`). `src/core/Inventory.ts` — 16-slot backpack + gold singleton (stacking, buy/sell/use). `src/core/Equipment.ts` — 5 equip slots (weapon/head/chest/legs/boots), a thin layer over `Inventory` (equip/unequip just move an item across that boundary); exposes `weaponDamage` and `defenseReduction` (diminishing-returns armor mitigation, see `EQUIPMENT` config). `src/core/Quests.ts` — quest-log singleton (`available`/`active`/`completed` per quest from `GameConfig.QUESTS`); collect-objective progress is read LIVE from `Inventory` (not stored), so selling the items lowers it and turn-in consumes them + grants the reward. `src/core/Items.ts` — item id/type helpers over `GameConfig.ITEMS`. `src/core/Skills.ts` — learnable-abilities singleton (one-off unlocks bought with skill points at a trainer NPC, from `GameConfig.SKILLS`); `skinning` gates boar-hide loot. `src/core/Save.ts` — **four save slots** (`SlotId`: one `"auto"` + three manual), each its own `localStorage` key. The autosave writes on every Progression/Inventory/Equipment/Quests/Skills/Dialogue change exactly as the single save always did; manual slots write only when the player asks. `TitleScene` and the PlayerPanel "ZAPIS" tab are the only things that call `load()`/`clear()`. Bump `SAVE_VERSION` when the save shape changes — a mismatched save is discarded (fresh run), never migrated. `src/core/Session.ts` — the playtime clock the slot cards are read from, ticked in `GameScene.update()` so paused menus don't count.
- `src/entities/Enemy.ts` — **config-driven base** enemy (patrol/chase/contact-damage/knockback/death/HP bar, all from an `EnemyConfig`) with protected hooks (`updateChase`, `canDeaggro`, `onLoseAggro`, `onGainAggro`, `updateAnimation`, `postMove`, `onHurt`, `onDeathVisual`) and a public `aggro()` so one creature can wake another. `onHurt`/`onDeathVisual` are one-shot hooks fired from `takeDamage`/`die` for a subclass with a real sheet to play a hurt/death clip — added for Wolf, default no-op, reusable by the next creature. **`postMove` fires right after patrol/chase has written the frame's velocity, to SHAPE it** — added for the rabbit's hop, whose gate has to apply to wandering and chasing alike while `patrol` stays private. It sits **inside** the knockback guard (an impulse owns the body outright, so there is no AI velocity to shape) and **before** `updateMotionFx`, which is the whole reason it isn't done in `updateAnimation`: the lean/stretch would otherwise still be computed from the ungated glide it exists to replace. A new enemy is a config block + subclass + map spawns, not a forked AI. The five:
  - `Rabbit.ts` — base + RABBIT config, plus **hop locomotion and the sploch** (see the checklist entry below), and the `updateAnimation` override that plays its real idle/walk/run sheet (see rabbit.png below).
  - `Boar.ts` — telegraphed charge (approach→telegraph→lunge→recover); also has a real idle/walk/run sheet via the same `updateAnimation` hook (see boar.png below).
  - `Wolf.ts` — **pack AI**: orbit at `pack.circleRadius` → dart in → peel off, plus a **howl** that pulls every wolf-kin within `pack.callRadius`. Also the base class for the Szary. Has a real 4-direction idle/walk/growl/bite/hurt/death sheet (wolf.png) — see boar.png/rabbit.png below — gated to `kind === "wolf"` so the Szary, who inherits from Wolf but has no directional sheet of his own yet, never touches it.
  - `GreyWolf.ts` — **Szary**, the named elite from the prologue: bite-and-backstep duel + an enrage phase under 40% HP. Has his own directional sheet (greywolf.png — bigger, paler, heavier-browed, scarred; NOT wolf.png at a larger scale) via the same `Wolf.updateAnimation`/`onHurt`/`onDeathVisual`/`playOneShot` machinery, pointed at his own texture through `this.animFn`.
  - `Spider.ts` — the ranged/support enemy: holds a firing band, retreats out of melee, spits a slowing web.
- `src/entities/Projectile.ts` — enemy shots (currently only the web) + the `ProjectileHost` interface `GameScene` implements. Entities fire through that interface rather than importing GameScene, which would be a cycle.
- `src/entities/Player.ts` — self-contained player (movement, combat, death). `src/entities/Merchant.ts` — stationary NPC (static portrait frame, immovable body). `src/entities/Loot.ts` — ground item drops (bob idle, lifetime despawn, no movement).
- `src/scenes/BootScene.ts` (load + placeholder setup) → `TitleScene.ts` ("Kontynuuj"/"Nowa gra", see Save.ts above) → `GameScene.ts` (gameplay) + `UIScene.ts` (HUD/controls, runs in parallel as an overlay).
- `src/ui/VirtualJoystick.ts`, `AttackButton.ts`, `HUD.ts` — touch controls + HUD, communicate with gameplay only via `InputState`/`Controls`/`GameEvents` (no direct scene reach-through). `src/ui/PlayerPanel.ts` (character sheet + backpack + quest log + minimap + save slots, as five tabs on one frame — `C`/`B`/`L`/`M`/`Z` open straight to a tab, switch tabs, or close) follows the same pattern. **NPC interaction is a dialogue hub**: `src/ui/NpcDialog.ts` owns the whole conversation (proximity, the `E` key, the prompt, and the game pause) and hands off to exactly one focused view at a time — `ShopPanel.ts` (buy/sell), `QuestPanel.ts` (accept/turn-in) or `TrainerPanel.ts` (learn skills). Those three deliberately **do not pause/resume on their own** — the pause belongs to the conversation, or stepping from the shop into the trainer would briefly unpause the world. Keys: `E` ends the conversation from any layer, `ESC` steps back one level (view → dialogue → closed). All panels extend `src/ui/PanelBase.ts` (shared chrome: container, background, close button, tooltip, `makeButton()`, centre-on-screen, pause-while-open); shared text styling/colours live in `src/core/theme.ts` (`UI` palette + `textStyle()`), and one-shot combat/loot FX (floating numbers, expanding rings) in `src/core/Fx.ts`.
- `src/world/TiledMap.ts` — loads maps authored in **Tiled** (JSON export). This is the primary map path; read the header comment before touching it (required export settings + why collision is flattened by hand).
- `src/world/MapBuilder.ts` — the original code-authored map (`GROUND` array + `OBJECTS` list). Now the **fallback**, used only when the Tiled JSON or Teren.png is unavailable, so the game always boots. Its four tile picks point into two regenerated sheets, so cross-check them against `docs/kafle.json` after any `build_tilesets.py --od-zera`; there is no bridge art any more and that entry deliberately draws a colour block.

## Maps (Tiled)

The starting location is `public/assets/maps/forrest.tmj` — an **80x60**
(2560x1920px) forest with a river, a ford, a road spine and a trader's glade in
the NE, wired as `MAPS.forest` and loaded by BootScene/GameScene. It is
**generated by `tools/build_mapa.py`**, not painted by hand; the script prints a
report and writes nothing unless given `--zapisz`, because once the map has been
touched in Tiled the `.tmj` is the source of truth and re-running would erase
that work. A second identical copy lives at `public/assets/forrest.tmj` (same
content, different relative PNG path, so it opens in Tiled from where it sits);
the game reads the one under `maps/`. `forrest.json` + its `.bak*` files are a
superseded export from the old tilesets — nothing reads them.

**Two sheets, two tilesets.** `Teren.png` carries the surfaces you walk on
(grass, dirt, sand, stone, water plus blob-47 transition sets) and `Nature.png`
carries the props that stand on them (tufts, bushes, trees). The split is
practical, not aesthetic: one blob-47 set is 47 tiles and the terrain keeps
growing, so sharing a sheet would renumber the trees on every terrain addition.
`TILESET_TEXTURES` in `TiledMap` maps a tileset's NAME inside the Tiled file to
the texture key we loaded it under — `Teren`, `Nature`, `Buildings`, `Kuznia`,
plus `Pole`/`pole_tileset` (crops, painted by the village's `pola`/`uprawy`
layers — see the note below). Three things follow, all of which have already
bitten once:
- **The name is the join, not the image path.** Rename a tileset in Tiled and
  its tiles stop drawing until this table is updated.
- **An unknown or unloaded tileset is skipped, not fatal** — the map still
  builds, minus those tiles, with a console warning. Only
  `MAPS.requiredTilesetName` ("Teren") is mandatory: a map missing its props is
  a bare field you can still walk around, a map missing its ground is nothing.
- **Collision is keyed `tilesetName#localId`, not by local id alone.** The name
  is what lets duplicate embeds of one sheet share their shapes; but with two
  DIFFERENT sheets, plain local ids collide outright (Teren's tile 16 and
  Nature's tile 16 are different pictures) and a tree's collision box would
  silently start blocking a doorway.

**`pole_tileset.png` (crops) was registered ahead of any map using it, and now
has its first real use.** `tools/build_pole.py` produced it for a while before
anything loaded it, so painting the three-field rotation from
`docs/wioska_plan.md` §4.5 would have ended in an evening's work rendering as
nothing but a console warning — the second bullet above, in its worst form.
Measured, not assumed: 461×395, **14 columns × 12 rows, 32px tiles on a 33px
pitch**, 163 of 168 cells filled, gap columns verified fully transparent.
Registered under BOTH `Pole` and `pole_tileset`, because Tiled names a new
tileset after its image file and a name mismatch is the same silent failure —
the same reason `NPC_OBJECT_NAMES` takes English and Polish spellings.
**As of E1 (2026-08-10) `village-zagaje.tmj` actually paints it**: a new
`pola` tile layer (inserted before `buildings` in draw order, same reasoning
as `path`/`undergrowth`), tileset firstgid 571 (right after Kuznia's
514+57).
- **All three niwy of the three-field rotation are now painted (E1 closed,
  2026-08-11)**: **północna** (fallow, x18-46/y27-36), **południowa** (rye,
  x18-46/y77-86, west of the road) and **wschodnia** (oats/barley alternating
  with flowering flax, x66-78/y70-86). ~595 soil + ~492 crop tiles.
- ⚠ **The fallow is painted to a DIFFERENT rule than the other two, and that
  difference is the whole point of a three-field rotation.** It keeps the same
  structure (horizontal zagony, 2–3 rows) but only ~48% coverage: some bands
  ploughed, some stubble, some greening over, some left as bare grass where
  Gniewko's sheep graze (`wioska_plan.md` §4.5/§5.9). Painted as densely as
  the rye it would stop being fallow, and three identical fields show three
  fields, not a rotation. It started as 20 token tiles, which read as a symbol
  next to two full fields once those existed.
  - Its palette avoids the second layer almost entirely: `ugor_bruzdy_pion_*`
    (id18/20/21) and **`pedy_kielki_*` (id25-28)** are both `grunt` at 1.00
    coverage — the latter is soil with green shoots, exactly "resting land
    growing over". Only the stubble (`sciernisko_sloma_*`) is `nakladka` and
    needs soil under it.
  - **Meadow herbs are left standing in its gaps on purpose.** `HERBS[*].
    siedlisko` puts rumianek and krwawnik in open sun — a fallow is their
    *correct* habitat, unlike the rye field a krwawnik had to be moved out of.
    The generator skips a 1-tile radius around each stanowisko, and because
    the fallow is patchy anyway the gap doesn't read as a hole.
  - **It takes TWO layers, and that is forced, not stylistic.** Of 13 grain
    tiles only 3 are `rola: grunt`; of flax and `nac`, **none**. Painting the
    crop on one layer would mean either three tiles for a whole field
    (visibly repeating) or holes in it. So `pola` carries the SOIL
    (`grunt`+`czysty` tiles) and a new `uprawy` layer carries the CROP
    (`nakladka`), showing the furrows through its gaps — the same split
    `buildings`/`buildings-detale` already uses. `TiledMap` handles layers
    generically (`-over` is the only special case), so this needed no code
    change.
  - **Strips run PERPENDICULAR to the road** (`wioska_plan.md` §4.5) — the
    main road is vertical at x50-51, so the zagony are horizontal bands 2–3
    rows tall. ⚠ **Adjacent bands must never share a crop variant**: there is
    no baulk tile between zagony, so the variant change is the *only* thing
    drawing the boundary — two identical bands merge and the striped reading
    disappears.
  - **Root crops are excluded on purpose.** Of the 17 tiles `build_pole.py`
    cut in half (bottom in the sheet, top in a loose `pole_over_NN.png`),
    **16 are `korzeniowe`** — the odd one out is `pedy_mlode_5`. Without a
    working `-over` layer they'd render topless. Grain and flax are whole,
    which is why the other two niwy could be painted now, and it is also why
    B6 (vegetable beds) is a *placement* job rather than an art one: cabbage
    (12 tiles, 3 growth stages) and `nac` (29) are all complete. See
    `polowka` in `docs/pole.json`.
  - A yarrow (`krwawnik`) stanowisko sat inside the eastern niwa. Cutting the
    field around it left a 5×5 clearing that read as a glade — the fix was to
    **move the stanowisko** to open meadow just east (74,82 → 80,74), since a
    niwa is authored content while stanowiska are deliberately more numerous
    than the plants standing on them (`GATHER.activeRatio`).
- **It now HAS a semantic catalog** — `docs/pole.json`, written by
`tools/katalog_pole.py` (2026-08-10), closing the last sheet that had
none. The split is deliberate: **measured on every run** — opaque
bounding box, coverage, colour shares, and `trawa` (which edges meet
turf, i.e. whether a tile is an edge tile of the strip); **read off the
sheet once** — crop species, growth stage, and furrow direction.
Automatic furrow detection was tried and rejected: row variance latches
onto the grass band (transition tiles scored as the most "furrowed" on
the sheet) and frequency analysis latches onto the rhythm of the PLANTS
(top scorers were cabbage and turnip, not ploughed earth).
- **The sheet mixes GROUND tiles with bare PLANT sprites on transparency**,
  because tiles are cut by connected-component labelling — a "tile" is
  however much joined into one component. Coverage runs continuously from
  0.12 to 1.00, so the catalog tags each tile `rola`: **`grunt`**
  (coverage ≥ 0.95, **68 tiles**) covers its own cell and may be laid as
  solid field; **`nakladka`** (95) needs soil underneath.
- ⚠ **`_dopelnij_krawedzie` in `build_pole.py` is what makes this sheet
  safe to hand-paint in Tiled — don't remove it.** Each tile is scaled by
  a uniform factor, then centred horizontally and bottom-aligned, so
  `round(w * skala)` lands on 29–31px instead of 32 and leaves 1–3px of
  transparency at an edge. On the map that is **a hairline gap showing the
  grass underneath** — reported as exactly that ("kafelki działek nie
  pasują"). Extending the edge pixels into that margin took fully-covering
  tiles **11 → 56** and `grunt` **38 → 68**, with zero change to any
  original pixel (verified against a pre-change copy).
  - **Going by the opaque bounding box does not work.** A *partially*
    transparent edge column is the common case: id6 had 28 of 32 pixels
    empty in column 0, so `xs.min()` was 0, the bbox test never fired, and
    the seam survived down 7/8 of the tile. Copy from the immediate
    neighbour instead.
  - ⚠ **The "is this even ground?" gate is mandatory.** The tempting and
    **false** assumption is that copying from a neighbour is self-limiting
    because a plant's margin has a transparent neighbour too — true only
    until a plant touches the tile edge, and several do. Without the gate,
    id90 grew a horizontal smear pulled out of its flower to the right
    edge and id147 a green bar down its whole left side. Both are obvious
    on a before/after render and invisible in any numeric report.
  - The split is clean, not arbitrary: a ground tile's central 16×16 block
    is 0.99–1.00 opaque, every plant is at most 0.78 (densest `nac` 0.78,
    a seedling 0.32) — an empty gap between the groups, so the 0.99
    threshold isn't balanced on anyone's edge. Margins wider than 3px are
    deliberately left alone: that's real shape, not rounding.
- ⚠ **An edge STRIP alone does not identify an edge tile — check the
  CORNERS too.** A tuft of turf sitting in one corner is a dozen-odd
  pixels out of a ~124px edge strip, about 0.15, under the 0.25 edge
  threshold. So **id6** (green block in its bottom-right) and **id11**
  (same, bottom-left) — a matched pair of *corner* tiles — were catalogued
  as clean `ugor`, i.e. as field interior, and one of them got painted
  into the middle of Zagaje's strip where it read as a tuft of grass
  growing in the field. Spotted by the user from a screenshot; no number
  in the report showed it. The catalog now measures corners separately
  (10×10 block, threshold 0.12) and carries `naroznik`.
- **For a field interior, use only tiles with `czysty: true`** (not one
  green pixel anywhere). There are exactly **four** on the whole sheet:
  `ugor_bruzdy_pion_2/4/5` (id18/20/21, vertical furrows) and
  `ugor_bruzdy_poz_2` (id2, horizontal). `katalog_pole.py` prints that
  list at the top of its report. Zagaje's strips are painted from the
  three vertical ones, mixed so a single repeated tile doesn't reveal the
  grid. The two niwy from §4.5 (south:
żyto, east: jarzyna/len) are still unpainted.
- ⚠ **The `-over` half does NOT work yet, and cannot without new asset work.**
  `build_pole.py` writes the tall plants' upper halves as **17 loose
  `pole_over_NN.png` files of natural size** (8–24px tall, some 33–35px wide,
  i.e. wider than a tile) rather than a sheet. Phaser binds one image per
  tileset, so a Tiled "collection of images" cannot be bound here at all.
  Tall grain therefore cannot be walked behind until those are packed into
  their own 33px-pitch sheet **and** their ground-tile pairing (`pary` in the
  generator) is exported as a catalog, the way `docs/budynki.json` does it.
  Low crops (ploughed earth, cabbage, roots) need none of that and work today.

Both sheets are 640px wide while 19 columns at a 33px pitch occupy 626, so
Phaser logs `Image tile area not tile size multiple` for each. It is a warning,
not a fault — verified in-engine that the geometry still resolves exactly
(Teren 19x12 = 228 tiles, Nature 19x7 = 133, on the 33px pitch).

**A fourth tileset, `Kuznia.png` (forge/smithy equipment — piec, kowadło,
oselka, stojaki…), is embedded the same way**, bound at

**Layers, one per kind of thing.** Everything green on one layer is
unmaintainable: fixing a single tree in a thicket would mean cutting it out
from under the grass tufts.

| layer | contents | sheet |
|---|---|---|
| `ground` | grass, variants mixed | Teren |
| `water` | river + backwater (blob 47) | Teren |
| `sand` | the ford's shoal (blob 47) | Teren |
| `path` | roads (blob 47) | Teren |
| `undergrowth` | grass tufts | Nature |
| `bushes` | bushes | Nature |
| `pola` | field SOIL — village only, `grunt`+`czysty` tiles | Pole |
| `uprawy` | the CROP standing on it — village only, `nakladka` tiles | Pole |

| `buildings-detale` | doors, windows (overlays onto the wall) | Buildings |
| `trees-base` | the BOTTOM row of every tree | Nature |
| `trees-over` | everything above it — drawn ABOVE entities | Nature |
| `buildings-over` | roofs — drawn ABOVE entities | Buildings |
| `objects` | spawns | — |

Splitting a prop across a base layer and an `-over` layer is the only way the
player can walk BEHIND it: a layer whose name ends in `-over` gets
`DEPTH.overhead`, everything else sits under the entities. The trunk tile has
to stay underneath, or the crown would cover a player standing *in front of*
the tree. When editing in Tiled, a whole-tree stamp lands on ONE layer — move
its bottom row to `trees-base` afterwards.

**Buildings split by a computed line, not by "bottom row".** `kafle_domu` in
`tools/build_mapa.py` decides which rows are roof (`buildings-over`) and which
are wall (`buildings`); the tree rule would be wrong here — a wall is two tiles
tall, so a player standing beside it would vanish behind their own house.
One building is placed today: the hunter's cabin in the NE glade (tile 64,3),
with the Hunter standing at its door. It deliberately keeps the **rectangular**
ridge roof (`styl="kalenica"`, the default): it has been on the map from the
start and switching it to the `/\` roof would change its height, while the
distances around it to the campfire, the blacksmith and the spawns are already
measured and asserted. New village buildings use `styl="szczyt"` plus
`material="deski"`, `wrota`/`drzwi_pol`/`klapa`/`otwor_siana`/`otwarty=(od,do)`
— barn, cowshed, chicken coop and stable are descriptions, not new art.

**A map with no object layer loses its whole roster, silently.** Without a
`player` object the spawn is found by scanning open ground, and with no object
layer at all the enemy list falls back to `defaultEnemySpawns` — three rabbits.
Re-exporting from Tiled without the object layer therefore looks like "the map
works, the game is empty". Check the layer survived the export before debugging
anything else.

**An empty enemy list is NOT that failure, and telling the two apart needs
`hasObjectLayer`.** "This map has no enemies on purpose" and "this map's object
layer vanished" both arrive as an empty `enemySpawns`, and the fallback above is
written only for the second. `TiledMap` therefore reports whether any object
came through at all; a map that authored objects clearly exported its layer, so
GameScene honours zero enemies as a decision. **This was a real bug**: the
village authors no enemies, so the safety net fired and scattered three rabbits
around Zagaje's own `player` point — which, once that point moved to the plaza,
put wild animals outside the Sołtys's door. A map wanting enemies still just
authors them; the code map (`MapBuilder`) has no object layer at all and keeps
its rabbits. Its
**object layer** carries the spawns as named point objects: one `player`, plus
`rabbit` / `boar` / `wolf` / `greywolf` (accepted as `szary` too) / `spider` —
`TiledMap.readSpawns` maps those names to typed `EnemySpawn`s — plus any number
of `campfire` points, an optional `merchant` (also accepted as `hunter`) and a
`blacksmith` (`kowal`). Both NPCs fall back to procedural placement when
unauthored, so a map without them still works.

**Spawn distances are load-bearing, not decorative, and `build_mapa.py` checks
them on every run** (prints OK/BLAD per rule, so a hand edit that breaks one is
caught by re-running the report):
- The three pack wolves sit **115 / 132 / 133px** apart, so any one of them
  links the whole trio through a single howl (`WOLF.pack.callRadius` = 200).
- The **Szary is 296px** from the nearest of them — outside that radius — which
  is the only thing stopping a pack howl from dragging a 190 HP elite into a
  three-wolf fight. The margin over 200 is deliberate: at 211px, nudging one
  wolf two tiles in Tiled would flip it.
- The **campfire is 119px from the Hunter**, which must exceed
  `MERCHANT.interactRange + CAMPFIRE.interactRange` (48 + 44 = 92). Two circles
  further apart than the sum of their radii cannot overlap, and that is what
  lets the shop and the fire share the `E` key without one press firing both.
  The **Kowal** is 128px from the Hunter (needs > 96 = two interact ranges) and
  161px from the fire.
- Two of the three spiders sit inside a boar's `aggroRange` (175) — that
  pairing is the whole point of the spider, since its web is what makes the
  boar's dodgeable charge undodgeable. The third stands alone, to teach what
  the web does before it matters.

The forest itself is a density field, not a scatter: an edge wall around the
whole map, a gradient toward the south-west (where the pack lives — that
darkening is the only warning the player gets before the first howl), and
large-scale noise for real thickets and real glades. Three layout bugs were
caught only by compositing the whole map to a PNG and looking at it, never by a
number: a ford that severed the river along the entire valley, a horizontal
road that cut a channel through the lake, and a forest that read as an orchard
because the density noise was too shallow. **Look at the map, don't just read
the report.**

Export from Tiled with: **JSON** format, **Tile Layer Format = CSV**
(base64/zlib yields a silently empty map — Phaser has no decompressor),
**Infinite off**, and **Embed Tileset** (external `.tsx` references are rejected
outright).

Two authoring rules that are easy to get wrong:
- **Flat terrain -> tile layers. Anything the player walks behind -> an `-over`
  layer.** A tile layer draws as one batch and cannot Y-sort per tile, so a tree
  crown painted onto an ordinary layer can never be walked behind.
- **Collision is flattened across layers**: for each cell the *topmost
  non-empty* tile decides passability. That's what makes a walkable bridge over
  solid water work without special cases. Note the consequence with `-over`
  layers — a crown tile painted over a solid trunk cell would make that cell
  passable again.

**The two maps' gate coordinates are NOT duplicated — they're read from
`tools/portale.py`,** a third module with no dependencies that both
generators import. A portal needs the SAME numbers on both ends (where the
gate sits, and where the OTHER map lands you), and keeping two independent
copies is exactly the class of bug that cost real time on the roof tiles
this session (two hand-maintained numbers drifting apart the first time
either map's layout changes). `tools/build_mapa.py` also had to grow its
road spine north by a few tiles (`ODNOGA_Y` used to be where it stopped) —
a gate with no road reaching it is a repeat of the campfire-in-a-field
mistake, just for a portal instead of an NPC.

**Engine side:** `TiledMap.ts` reads Tiled point objects named `"portal"`,
decoding Tiled's custom-properties array (`[{name,type,value}, …]`, copied
through unchanged by Phaser's parser — see `readProps`) into a `target` map id
plus a `spawnX`/`spawnY` pair **in the target map's own pixel space**.
`GameScene` carries the crossing through `scene.restart({mapId, spawn, hp})`
— restart re-runs `init()`/`create()` on the same "Game" scene key, which is
why `MAP_BY_ID` maps a short id ("village") rather than a Phaser cache key:
the portal object shouldn't need to know how the target map's JSON was
loaded. Three things worth knowing if you touch this:
- **A portal is walk-through, not an interact prompt** (`PORTAL.triggerRadius`,
  update()) — a gate is geography, the way loot pickup already is, not an NPC
  needing `E`.
- **HP is carried explicitly (`pendingHp`) and would otherwise be a free full
  heal.** `Player`'s constructor always seeds HP from `Progression.maxHp` —
  fine for the very first `create()` a session ever does, but portals are the
  first time `create()` re-runs *during play*, and skipping this would let a
  player heal by walking through any gate, undercutting the whole
  regen/food/potion economy the RESPAWN-cost design fought to protect (see
  that note lower in this file).
- **The arrival point on each side sits outside the OTHER side's trigger
  radius on purpose** (a few tiles past the gate, not on it) — landing inside
  your own return trigger would bounce you right back. Verified in-engine:
  a full forest→village→forest round trip lands at the exact authored pixel
  each time, HP unchanged (regen aside), with no scene/listener leaks across
  two restarts.
- **`tools/portale.py` defines exactly FOUR points and the maps must carry
  exactly those.** The village had picked up a fifth: a second `portal` object
  at (1646.36, 3151.82) — fractional coordinates, i.e. a copy dragged in Tiled
  at a non-integer zoom — 30px from the real gate, with the same `target` and
  the same arrival. Harmless in play (the trigger loop breaks on the first
  match) and exactly the drift that module exists to prevent, so it is gone.
  If a gate ever needs to be wider than one point, widen it **in
  `portale.py`**, on both maps at once; do not park a second object next to
  the first. Known and deliberate consequence of one point per gate: with
  `PORTAL.triggerRadius` at 28 the trigger spans 56px across a road that is
  two tiles (64px) wide, so a player hugging the far edge can walk past it.
  Both gates behave identically in this, there is no collision to stop anyone
  leaving the map elsewhere anyway, and the fix (put the gate on the road's
  centre line rather than a tile centre) is a `portale.py` change nobody has
  needed yet.


## Assets — read `public/assets/README.md` before touching extraction code
Every pixel-layout fact in there was measured directly from the PNGs (Python/PIL alpha-channel analysis), not guessed. Highlights, so you don't have to re-derive them:

- **`Teren.png` (640×395, surfaces) and `Nature.png` (640×230, props)** are both real 32×32 tile grids on a **33px pitch** (1px transparent gap between tiles), 19 columns each. Both are **regenerated** by `tools/build_tilesets.py`, so any hard-coded (col,row) pick into them is a coordinate with no owner — see the campfire below. Multi-tile props are stitched with `extractTileGrid()` — a deterministic block-copy, **not** alpha-scanning. A prior alpha-scanning approach (`extractCompact`) got fooled by a single stray opaque pixel from a decoration bleeding into a gap column and left a visible seam; don't bring that pattern back for these sheets.
- **A tile pick into a regenerated sheet fails silently.** The campfire used to be cut from Nature.png at pixel (132,198); rebuilding the sheet moved everything and that crop became part of a tree crown. The extraction still "worked". It is now always generated (`makeCampfirePlaceholder`), and the rule is: if code needs a tile from these sheets, give it a **named entry in the generator** first, not a coordinate.
- **Character.png** frames sit on a ~31×60 pitch (not a clean 32-grid) — explicit pixel offsets, not divide-by-count slicing. Column 4 of each direction row is the **attack pose**, excluded from the walk cycle. There's a separate small **sword icon** elsewhere on the sheet, extracted and attached to the player as a rotating child sprite during the attack pose.
- **Known art limitation: the left/right attack pose swaps hands.** Rows 2 (`left`) and 3 (`right`) of Character.png are pixel-for-pixel horizontal mirrors of each other (verified — diffing the attack frame of one against a flipped copy of the other shows near-zero difference in the arm/hand region). Mirroring an asymmetric figure swaps its handedness, so the arm that swings the weapon reads as the character's right hand when facing right and left hand when facing left, even though `ASSETS.character.handOffsets` documents all four as "the right hand" (that comment describes the code's *symmetric offset convention*, not a true anatomical guarantee). This is not a code bug — `Player.ts` never applies `flipX`; the mismatch is baked into the source PNG. A pixel-composite fix was attempted (pasting the `right` row's arm onto the `left` row's body) and rejected — at 31×60px it reads as visibly glued-on (arm at the wrong angle, a stray sleeve fragment, no shoulder attachment). Truly fixing this needs a hand-drawn "left-facing, right-hand cross-body swing" attack frame from a pixel artist, not a scripted edit. Leave the current mirrored art as-is until that exists.
- **rabbit.png** (96×72, generated by `tools/build_rabbit.py` — see `public/assets/README.md`) is a real directional sheet: idle down/up + a 4-frame hop cycle in profile (walk + run rows), reused mirrored via `setFlipX` for left/right instead of drawing both sides. Rabbit and Boar are the two enemies with an actual walk/run cycle (`updateAnimation`, driven by `Enemy`'s `updateAnimation` hook) rather than relying on the procedural motion FX alone — **but only for horizontal-ish movement**; movement dominated by the vertical axis still falls back to the static idle-down/idle-up frame, a deliberate scope cut matching every other enemy's baseline (not an oversight).
- **boar.png** (112×84, generated by `tools/build_dzik.py`, the sibling of `tools/build_rabbit.py` — see `public/assets/README.md`) is the second real directional sheet: same idle down/up + walk/run grid shape as `ASSETS.rabbit` (both slice through the one shared `sliceCreatureSheet()` in Assets.ts, and both animation sets are built by the one shared `createCreatureAnimations()` in Animations.ts), just a bigger frame (28×28) and a heavier quadruped trot instead of a hop. `Boar.updateAnimation` picks walk/run the same speed-threshold way as `Rabbit`, and never touches `setFlipX` while stationary — the charge's telegraph/recover phases already set their own facing and must not be snapped back by a momentary zero velocity.
- **wolf.png** (112×672, `tools/build_wilk.py`) and **greywolf.png** (128×768, `tools/build_szary.py`, the Szary's OWN sheet — see below) are the richest sheets yet: 6 states (Idle/Walk/Growl/Bite Attack/Hurt Reaction/Death) × 4 **independently drawn** directions each — the first creature sheets where left/right are NOT a mirrored runtime flip (rabbit/boar deliberately draw only 3 directions + `setFlipX`; the user wanted true 4-direction art here, so "left" is baked as a real mirrored frame inside each Python script instead). `Enemy` grew two new one-shot hooks for this: `onHurt()` (called from `takeDamage`, only on a hit that's survived) and `onDeathVisual()` (called at the top of `die()`, before the fade tween) — both default no-ops, reusable by the next creature with a sheet. `Wolf.playOneShot` plays growl on `howl()` (the pack alarm) and bite on `enterLunge()` — deliberately **not** before every lunge, which would add a telegraph the pack's dart is designed not to have (see the `lungeMs`/`lungeSpeed` comment in Wolf.ts); `GreyWolf` plays growl on `enterWindup` (his REAL telegraph — the whole reason this pays off for him specifically) and on `checkEnrage`, and bite on `resolveBite`. **Gotcha worth remembering if you touch this again:** the pre-existing `setFlipX` calls in `circleStep`/`enterLunge`/`patrol`/GreyWolf's `close` phase (written when every wolf-kind creature was one generic always-facing-right texture) had to be forced off (`this.setFlipX(false)` at the top of `Wolf.updateAnimation`) — left on, they'd mirror the already-correct 4-direction frames a second time, so a wolf moving left would show frames that read as facing right.
  - `Wolf`/`GreyWolf` share one animation implementation (`updateAnimation`/`onHurt`/`onDeathVisual`/`playOneShot`, all in `Wolf.ts`) that reads which sheet to use from `this.animFn`, a function assigned in the constructor **body** (`Wolf` defaults to `wolfAnim`, `GreyWolf`'s constructor passes `greyWolfAnim`) — not a class-field default, because a subclass's field initializers run AFTER `super()` returns, which would still be Wolf's default at the point the base constructor's own initial `this.play(...)` call runs. This is also what let GreyWolf inherit correct behavior for free the day he got his own sheet, with zero changes to those four methods.
- **the spider and the web shot have no PNGs at all** — those textures are *always* generated procedurally (`makeSpiderPlaceholder` / `makeWebPlaceholder` in Assets.ts, driven by `ASSETS.spider` / `.web`), so those blocks have no `key`/`path`. Drop e.g. an `assets/spider.png` in and wire a real extraction when art exists; same "always boots" guarantee either way.
- **pig.png** (104×78, `tools/build_swinia.py`) exists in `public/assets/` but **nothing loads it** — no `ASSETS.pig`, no entity. It's art staged ahead of need for the village's livestock (`docs/swiat.md`), same move as the barn/cowshed/coop tiles in Buildings.png existing long before the village does. Wiring it in later is the same four-step recipe as the boar: `ASSETS.pig` (same shape as `ASSETS.rabbit`/`.boar`) + `sliceCreatureSheet`/placeholder in Assets.ts + `createPigAnimations` in Animations.ts + a new entity class.
  - The Szary is drawn from the wolf's shape language but **paler, heavier-browed and scarred, at a bigger `face` size** — deliberately not the wolf texture at a larger `scale`, because two scales of one sprite read as perspective rather than as two different creatures.
- **NPC.png** shares Character.png's exact pitch (same alpha-scan boundaries) — only the idle-down frame is extracted, since the merchant never walks.
- **items.png** is a true 32×32 grid with **zero gap** (unlike Nature.png's 33px pitch) — plain block-copy extraction, no separator math. Only a curated subset of the 20×30 sheet is wired up; the exact (col,row) picks (and how they were verified — don't eyeball the thumbnail) are in the README.
- **Buildings.png** (640×230) is a **modular kit** generated by `tools/build_budynki.py` — 88 tiles: log walls and **plank walls** (3×3 each), **two thatched roof shapes** (rectangular ridge roof + the gable `/\` set), an open-fronted bay + post, a rail fence, and doors/windows/chimney/barn-doors/dutch-door/hay-hatch/chicken-hatch/haystack/trough as **transparent overlays** placed on their own map layer. Buildings are assembled from a one-line description (`BUDYNKI_NA_MAPIE` in `tools/build_mapa.py`, mirrored by `WZORY` in the generator), not stamped as whole-building props — two earlier attempts did that and were rejected: baking a door into a wall tile means every door position is a new set of walls, and a finished 4×4 house cannot become a 5×3 one. Tile ids and sheet size live in `docs/budynki.json`. **Adding tiles must go in NEW ROWS** — the id is `row*19 + column`, so appending rows leaves every existing id untouched (verified: `forrest.tmj` renders the hunter's cabin identically after the sheet grew from 3 to 6 rows), while inserting a column would renumber the map into mosaic. Three things carry the look, each learned the hard way (details in `public/assets/README.md`): **a log is a cylinder, not a stripe** (8px full profile), **a corner log-end is a disc**, and **thatch needs courses whose boundary waves** — dead-straight courses read as corrugated cardboard, per-column random ones as speckled fur. **Every period divides 32** (log 8, course 8, stone 8, plank 8, diagonal course 16); that is the only reason the middle tiles repeat seamlessly, and test [4] checks it against the 90th percentile of internal differences, not the median. `b1.jpg`/`b2.png` are Gemini reference sheets — 98k colours, zero alpha, reference only, licence unresolved; `a1.jpg`/`a2.webp`/`a3.webp` are the same kind of material for the village (shape vocabulary only).
  - **The gable roof is a CHEVRON, not a filled triangle.** The first attempt built a solid pyramid from ridge to base — a front-on view of a hip roof — and it was rejected on sight. A real gable roof has **constant thickness**: the ridge runs along its upper edge, the eave along its lower edge, both diagonal and parallel, and **the gable wall shows between the arms** carrying the attic window. A filled triangle eats that wall and the building loses the storey that is its main feature in every reference.
  - Three consequences, all forced rather than chosen: **width under a `/\` roof must be EVEN** (the ridge sits on a tile boundary, so the 45° diagonals land exactly on tile corners — an odd width puts the apex mid-tile and every roof edge steps at each row boundary); **the roof is a layer ABOVE the wall** (`buildings-over`, and the chimney goes there too — put in the overlay layer it vanished under its own roof), so the wall starts at row `GRUBOSC_DACHU` and must be at least `szer/2 + 1` rows tall or an arm hangs over grass; and **thatch courses run parallel to the eave, i.e. diagonally**, on a 16px period because 16 divides 32.
  - **The whole village is thatched.** One iteration repainted the gable planes as timber planking, reading the reference sheets as a guide to the *material* — they are a guide to the **shape**. The only wooden part of this roof is the ridge beam at the apex.
  - **Both ends of the ridge beam were reported as cut off, and each needs a different fix.** Bottom: a **round log face** — flat-cut it reads as unfinished ("the ridge looks half made"), and the disc straddles a tile boundary so each half must be drawn from a **fractional** centre or it splits along the axis. Top: the beam **tapers toward the apex**, 2px at the peak widening to 10px eight rows down ("the ridge is abruptly cut at the end") — a flat start at a fixed height puts a horizontal cut across the peak, and no taper at all fills the whole wedge and reads as a mast.
  - **The thatch field is computed from GLOBAL position** (fixed wave phase, deterministic straw), so courses run unbroken across tile seams. That is also why the roof plane is **one tile with no variants**: there is no lattice to break, and adding a variant would introduce the seam rather than hide it. The visible symptom of getting this wrong was a rectangular patch of misaligned courses around the chimney, whose tile carries its own baked background.
  - **EVERY band drawn along a diagonal spills out of the tile that carries that diagonal — this is the load-bearing rule of the whole kit.** The diagonal runs corner to corner, so a band *w* px wide pokes a *w*-sided triangle into the two tiles touching its ends, and those tiles are ordinary planes that know nothing about it. Caught three times, each time only on an assembled building: the **eave shadow** (→ its own `podokap` tile row; without it the roof's lower edge was a staircase, measured at 22px of drop over 31px of width, jumping back 10px per tile), the **thick eave edge** (11px → `_naroznik_okapu` glued onto the plane above the eave, `*_okp`), and the **ridge roll** (4px → `_naroznik_kalenicy` on the plane under the ridge, `*_kal`). Consequence: **tiles within the band are not interchangeable** — the top row touches the ridge, the bottom row touches the eave, and each must carry a piece of the other band.
  - Roof band thickness is **at least 3 tiles (96px), not 2**, and the generator rejects a thinner single tile rather than quietly placing a wrong one — in a top-front view the roof is the building's main mass and must read as a surface, not as a frame around the gable. Wider buildings need MORE than 3 (see the `lico` note below), so actual building sizes are cottage 8×9 tiles, barn 10×11, cowshed 8×9, coop 6×7 (stays at 3 — narrow enough that `dodatkowe` is 0), stable 9×6 (ridge roof, not gable, unaffected). Related: the ridge beam's round end belongs to the **last** band row only; the version that reused one tile for every plane row drew two log faces on one beam — invisible at thickness 2, obvious at 3.
  - **The chimney has its background baked into BOTH of its tiles.** There is one layer, so a cell cannot belong to the roof and the chimney at once — a chimney tile replaces the roof tile rather than overlaying it. This bit twice: first the lower tile cut a gap in the ridge, then the upper tile punched a grass-coloured hole in the gable plane. An empty background is correct only where the chimney genuinely sticks out above the roof.
  - **Where the wall begins (`lico`) must scale with building WIDTH, not be the flat constant `GRUBOSC_DACHU` — and the fix has to ADD roof tiles, not just move the wall.** Each column starts its own local band at row `d` (further from the ridge = lower), so the edge column's band doesn't even begin until row `szer//2 - 1`. A fixed `lico = GRUBOSC_DACHU` let the wall start before that column's roof had rendered a single fully-opaque tile — its corner log-end (the same disc-shaped "zamek" that marks every bale-wall corner) then sat exposed on bare grass, past the roof's edge entirely ("beams sticking out"; invisible at 6-wide, worse the wider the building gets). **The first fix attempt just pushed `lico` down to `max(GRUBOSC_DACHU, szer//2)` without extending the roof itself — which opened a *different* hole**: the ridge-adjacent columns had already finished their (unchanged) 3-row band by the old `GRUBOSC_DACHU`, so the gap between where their roof now ended and where the wall newly began showed bare grass right in the gable notch. Reported immediately: "you moved a row of tiles instead of adding a row of tiles, now we have a hole." The correct fix inserts `dodatkowe = max(0, szer//2 - GRUBOSC_DACHU)` extra, fully-opaque plain-thatch tiles into **every** column's band (not just the wide ones) before the eave, so the roof genuinely grows deeper for all columns together and the wall start moves down by exactly the same amount the roof grew. Two follow-on details, each caught by test [10], not by eye: the eave's baked-in thick-edge overlay (on the tile named `*_dol`/`*_okp`) is only correct on the tile *immediately* before the true eave, so it has to move to `r0 + lico - 1` rather than staying fixed at `r0 + 2`; and the ridge beam needs its own plain "still going, no cap yet" filler tile (`szczyt_fill`) for the inserted rows, or the beam visibly breaks in the middle before resuming at its round end. Kept identical across `_dach_szczytowy` in both `build_budynki.py` and `build_mapa.py`, and `build_mapa.py`'s standalone `wysokosc_budynku` estimate — all three must agree, since the wall-start row is exactly their shared seam. Test [11] composes a real building (roof and wall together, not just the roof) and checks every column for any transparent pixel between its first opaque roof pixel and the foundation — the only test that would have caught either version of this bug, since [8]-[10] only ever look at the roof in isolation.
  - Verification test [8] composes the whole roof and checks the band has no holes inside and nothing outside it — an off-by-one in a diagonal mask shows up as a grass-coloured seam down an entire arm, and that is invisible on a single tile. Test [9] catches the staircase specifically: on a 45° edge the sum (column + lowest opaque row) is constant, so its spread *is* the step height in pixels. **Test [10] is the one that matters most**: it compares every pixel of the band against a globally-computed reference (`_wzor_pasa`), which is the only way the interior spills show up at all — [8] and [9] look at the silhouette and both stay green while a band is broken (verified: disabling the eave corner leaves [9] at OK and [10] at 234 bad pixels).
- **Indoor.png** is still reserved for future interiors and has **not** been pixel-analyzed — don't assume it shares that pitch without re-verifying.
- If a PNG is missing, the game generates a colored placeholder and logs which file to add — it never fails to boot.

- ✅ **Enemy projectiles** (`src/entities/Projectile.ts`): the scene owns the group and both collisions; entities fire through the `ProjectileHost` interface. Two traps are documented in the code and worth repeating here, because both produce a bug that looks like nothing happening at all:
  - **Adding a body to an Arcade group resets it to the group's defaults** — including `setVelocityX/Y: 0` and `setCollideWorldBounds: false`. A velocity set in the constructor is silently wiped on `group.add()`. Hence `Projectile.launch()`, called *after* the add. Symptom when this was wrong: the web spawned, rendered, and hung motionless 168px from the player for 156 frames.
  - **Aim in BODY space, not sprite space.** Every entity anchors its collision body at the feet, well below the sprite centre, so a shot fired from one sprite centre at another passes *under* the target's hitbox — measured at 5px of clearance, i.e. a miss every single time, with nothing on screen to explain it.
- ✅ HUD (HP bar, XP bar, level, gold), red-flash + knockback + camera-shake hit feedback
- ✅ **The hit flash restores the state tint instead of clearing it** (`flashHit`'s `restoreTint`, `Enemy.setBaseTint`). This was a real bug and it silently disabled the game's entire telegraph vocabulary: every tell is a tint, and `flashHit` ended with an unconditional `clearTint()`. Measured before the fix — one hit on a boar mid-wind-up erased its red charge tell while `phase` was still `"telegraph"`, and one hit on the enraged Szary removed his red for the rest of the fight. Telegraphs only matter *while you are trading blows*, which was exactly when they were being deleted.
  - **Subclasses must go through `setBaseTint`, never `setTint`/`clearTint`.** Direct calls work until the first sword blow, then vanish — the worst failure mode for a signal the player is meant to react to.
  - **`restoreTint` is passed as a getter, not a value.** Resolving it at flash *start* restores a stale tell: hit a boar in the last frames of its wind-up and the orange came back **after** it had already launched, leaving it painted as if still winding up. A false tell is worse than none, because the player reacts to it. Verified: telegraph → red flash → telegraph restored → no tint once the phase moves on.
- ✅ **Hit-stop on crits** (`COMBAT_FEEDBACK.critHitStop`, `GameScene.critHitStop`): ~3 frames of frozen physics plus a short shake. Only physics is paused — tweens keep running so the damage number, swing arc and hit flash animate through the freeze; pausing everything reads as a dropped frame, not a punch.
  - **`minGapMs` is load-bearing, same idea as `AUDIO.minRetriggerMs`.** Crit chance reaches 60% and a dagger build swings ~3×/s, so an ungated hit-stop would stutter constantly. Verified: 240 frames of *forced* crits produced 10 freezes at an even 26-frame spacing, and a whirlwind catching five enemies freezes once, not five times.

The HP bar is 200px in a corner while the player is watching their thumb and the enemy, so death arrived as a surprise — which matters here because dying has a real price (half HP + 10% gold), and an unforeseeable penalty reads as unfair rather than tense. The texture is a canvas radial gradient built at boot (`makeVignetteTexture`), since Phaser shapes can't do gradients.

Both are announced on the death screen — a silently shrinking gold number reads as a bug.
  - **A full heal on respawn was a mechanical hole, not a balance one.** It made dying the cheapest heal in the game and quietly invalidated everything built around managing HP: out-of-combat regeneration (75s per half bar), food, potions, and the whole point of the boar's telegraphed charge. Don't restore `hpRatio: 1` without replacing the cost somewhere else.

- ✅ **Sound** (`src/core/Sfx.ts`, `AUDIO` config, `public/assets/audio/*.wav`): 16 effects + 1 looping bed — swing, hit, crit, hurt, enemy-die, loot, level-up, ability, drink, player-die, ui-click, **howl** (pack alarm + the Szary's enrage), **spit** (the web), **growl** (something has taken an interest in you: boar wind-up, wolf lunge, Szary wind-up), **charge** (the boar committing), **impact** (a heavy blow LANDING on you — boar charge, Szary bite; louder and lower than `hurt`, so "that one really hurt" is audible without reading the bar).
  - **A looping bed is started via `Sfx.startAmbient(key)`, never via `play()`** — it needs a handle to stop, must skip the retrigger throttle, and must survive the browser's autoplay block. That last part is the load-bearing bit: audio is refused until the first real user gesture, so a bed started in `GameScene.create` would simply never be heard; `startAmbient` hooks `Phaser.Sound.Events.UNLOCKED` when the manager is locked. Started in GameScene (not Boot — the title screen stays silent) and stopped on shutdown, or it would play on under the title after a restart.
  - **The bed is PER MAP (`MAPS.*.ambientKey`), not one global constant.** It used to be a single `AUDIO.ambientKey`, so Zagaje played the forest — wind, leaves and birds — and walking through the gate changed nothing in the ears. Ambience is the cheapest "this is a different place" channel the game has and spending it on one bed for the whole world wastes it. `village-ambient` is a lower, narrower air bed (70–700 Hz vs the forest's 90–700) carrying **events** rather than layers: a distant anvil in bursts of three, hens, one dog per loop. Two consequences worth keeping: it sits at 0.13 against the forest's 0.16, because a discrete event is far more noticeable than texture at the same level and a hammer that asks to be listened to has stopped being a bed; and the UNLOCKED hook now reads the wanted key off a **field**, not a closure, or the map you already left could decide what starts playing when the browser finally allows sound.
    - Measured against the same rules the forest bed was tuned to (the band note in `tools/gen_audio.py` is not optional reading): **0.8% of energy above 2 kHz** (the CRT-hiss failure was 24%), 85.3% in the 120–1000 Hz core, 9.1% below 120 Hz (the subsonic-rumble failure was 86–100%), envelope min/max 0.38/1.00 so it genuinely breathes, loop seam discontinuity smaller than the forest's.
    - **Append new sounds at the END of `SOUNDS` in `gen_audio.py`.** The seed is fixed but `rng` is shared and consumed in dict order, so inserting an entry in the middle shifts the stream and silently changes every file below it. Verified: adding `village-ambient` last left all 17 existing wavs byte-identical.
  - Deliberately ambience, not music: procedural music sounds like a synth demo, and the world's tone is "ciepły realizm". A bed works by being *missed when it stops*. Generated by `tools/gen_audio.py` like everything else — wind + leaves + bird pairs, **crossfaded end-to-start**, without which the loop seam clicks on every pass. `AUDIO.ambientEnabled` turns it off entirely: a permanent loop is the one sound a player cannot escape, so it gets a switch and not just a volume.
  - **The wind's frequency band is the whole ballgame, and it must be measured, not eyeballed.** Reported by the user as "continuous hiss like an old CRT television" — and it was: the first version filtered *white* noise through a **single-pole** lowpass (6 dB/octave), leaving **24% of the total energy above 2 kHz**. Overcorrecting is just as bad and just as easy: brown noise through four poles at 260 Hz put 86–100% of the energy *below 120 Hz*, a subsonic rumble a phone speaker cannot even reproduce. The bed is now shaped in the frequency domain (`band_noise`, 90–700 Hz), measured at **2.4% above 2 kHz** with the core in 120–1000 Hz.
  - **Constant amplitude is itself the "broken equipment" cue**, independent of spectrum: noise at a flat level reads as a fault, and only swelling and fading reads as weather. Envelope min/max is 0.37; the leaf rustle is likewise a handful of gusts, not a permanent layer.
  - The wavs are **procedural placeholders generated by `tools/gen_audio.py`** (numpy synthesis: noise + sweeps + envelopes, fixed RNG seed so reruns are identical). Same rule as the textures — drop a real recording in under the same filename to replace it. Re-run the script to retune.
  - **A missing file is never fatal.** `Sfx.init` checks the cache, warns once listing what's absent, and every later `play()` for that key is a no-op. Delete the whole audio folder and the game runs silently.
  - **`AUDIO.minRetriggerMs` (40ms) is load-bearing, not polish.** Wir ostrzy resolves against every enemy in range within one frame, so a five-rabbit swarm would fire five identical samples at the same instant — summed amplitude clips and reads as static. Verified: 4 enemies hit → 2 sounds (the `hit`s collapse, a `crit` still cuts through on its own throttle, which is the desired behaviour).
  - Volumes are deliberately uneven: `swing` sits at 0.3 because it fires up to ~3/s with Zręczność, while `level-up` gets 0.7 because it's rare.
  - **Wiring is split on purpose.** Events that already exist are hooked once in `Sfx.init` (leveledUp, playerDied, enemyKilled, heal/healOverTime). The rest are direct `Sfx.play()` calls at the exact moment: swing/hurt in `Player`, hit/crit/loot/ability in `GameScene`. Inventing events just to carry a sound would be worse.
  - `Sfx.init` runs in **BootScene**, not GameScene — that one restarts, and re-subscribing would stack duplicate listeners and play everything twice.
  - The ability sound fires **after** the readiness check, so tapping a cooling-down button stays silent. Same idea in `PanelBase.makeButton`: the click sound is inside the `enabled` branch, or a greyed-out button would sound like it worked.
  - **`NpcDialog.addOption` needs its own click sound** — the three hub rows (Handel/Zadania/Szkolenie) are hand-built there rather than via `PanelBase.makeButton`, so they don't inherit it. They're the most-pressed buttons in the game; silence there was noticeable.
- ✅ **Enemy HP bar** (`COMBAT_FEEDBACK.enemyHpBar`, drawn by `Enemy`): a thin bar over an enemy, **hidden until you have actually hit it**, fading out ~2.6s after the last hit. Green → yellow → red on the same thresholds as the player's HUD bar, so the colour means one thing everywhere.
  - Hidden-until-first-blood is deliberate: a field of permanent bars reads as a spreadsheet, and an untouched enemy is at full health by definition. Without any bar a boar (95 HP) is unreadable — you cannot tell whether it dies to the next swing or the fifth, which is exactly the call Unik and Okrzyk bojowy exist to serve.
  - The bars are created **hidden, once per enemy** in the constructor and destroyed in `die()` immediately rather than on the death tween's completion — an empty bar hanging over a corpse reads as a leftover. Verified no orphans: 16 bar objects for 8 enemies, 14 after one dies.
  - Vertical offset is measured from `this.height * cfg.scale`, **not** `displayHeight`, because the procedural breathe tween animates `scaleY` and reading the live height would make the bar bob.
- ✅ XP + levels (`src/core/Progression.ts`) — kills grant XP, levels grant skill points (**1 per level**, see the rebalance note below)
- ✅ Player panel (`C`/`B` or the top-right button — tabs, see Architecture): stats readout + spending points into Siła (melee damage) / Kondycja (max HP) / Zręczność (**attack speed** + crit), plus the backpack tab. Opening pauses GameScene.
- ✅ Crits: `PLAYER.critChance`/`critMultiplier` base (15%/180%), crit chance scaling with Zręczność (`ATTRIBUTES.critChancePerAgility`, capped at `ATTRIBUTES.maxCritChance`) via `Progression.critChance`, rolled per target, shown as floating damage numbers
- ✅ **Attack speed as a stat**: Zręczność grants `ATTRIBUTES.attackSpeedPerAgility` per point (capped at `maxAttackSpeedBonus`), applied in `Progression.attackCooldown` **and** `swingDurationMs` — both must scale together or the next swing starts before the attack pose finishes and the sprite visibly stutters.
- ✅ **Out-of-combat HP regeneration** (`Player.regenerate`, called from `GameScene.update`): `Progression.hpRegenPerSecond` = `PLAYER.hpRegenPerSecond` + Kondycja × `ATTRIBUTES.hpRegenPerEndurance`, and it only ticks once `PLAYER.regenDelayMs` (5s) has passed since the last hit **taken** — the classic five-second rule. This is what gives Kondycja a second dimension instead of being a pure max-HP dump. Three things here are load-bearing, don't "simplify" them:
  - **Out-of-combat only is a design decision, not a balance one.** It's what structurally protects potions (and the planned cooking/food tier): mid-fight there is no regen at all, so a potion is the only answer to damage during a fight. If regen ever ticks in combat, potions are defended only by keeping the number tiny — and that dies the first time Kondycja or regen gear is buffed. Intended tiers: regen = free/slow/out-of-combat, food = cheap/fast/out-of-combat, potion = expensive/instant/works in combat.
  - **HP is carried as a float.** The trickle is well under 1 HP/s at low Kondycja, so rounding per frame would floor it to zero and the whole mechanic would silently do nothing.
  - **`playerHpChanged` is emitted only when the whole-number HP moves** (or the bar tops out), not every frame — otherwise this fires ~60 events/sec and drags the HUD and character panel with it.
  `hpRegenPerEndurance` is deliberately `hpPerEndurance/150`, which holds "heal half your HP in ~75s" constant across every build (verified 77s at 0 Kondycja, 75s at 49) — change one and re-check the other. - ✅ **Rabbit: hop locomotion + the sploch** (`RABBIT.hop` / `RABBIT.panic`, `Rabbit.postMove`/`updateChase`). It was the last enemy with no mechanic. Two behaviours, and the ⏳ this replaced was right that "flee at low HP" needs a decision rather than a patch — what makes it work is that it is bounded twice over.
  - **It hops instead of gliding.** Movement is bursts with pauses, and **one hop is exactly one pass of the sprite's own animation cycle** — derived in `Rabbit.ts` from `ASSETS.rabbit`'s frame count and fps, never written down twice, so a retimed animation can't desynchronise from the movement it describes. The cycle is restarted at take-off so the animation's frame 0 is the frame the body actually leaves the ground on; `play(key, true)` alone lets the two drift apart within a couple of hops, which is the sliding this exists to fix. Measured: hop period **400ms**, exactly the run cycle.
  - ⚠ **`hop.pushFraction` is the duty cycle AND the speed compensation** — burst speed is `patrolSpeed`/`chaseSpeed` *divided* by it, so the average over a whole hop is what those fields already promised. That is what keeps every number tuned around them (aggroRange, deAggroRange, time-to-reach-you) meaning what it meant before hops existed. Measured in a 4s steady-state chase: burst **107.7 px/s** against a predicted 107.7, average **71.8 vs 70 (+2.6%)** — the residue is 60Hz quantization (15.6 frames of push rounds to 16), not a modelling error.
  - **Chase hops jink ±22°, patrol hops do not.** During patrol it would spiral around the wander target instead of reaching it. The jink is the part that makes landing the frontal arc a matter of timing rather than of walking up.
  - **Sploch: once, below 40% HP, it bolts flat out and then freezes** — 230px/s (above `PLAYER.speed`, so it genuinely opens a gap) then ~1.3s sitting motionless, which is the free window that is the payoff. The bolt is deliberately **not** hop-gated: everything else this creature does is a series of hops, and panic reading as one unbroken sprint is what separates it.
  - ⚠ **The bolt is bounded by DISTANCE (`panic.boltMaxGap`), not only by time, and the distance half is load-bearing.** Where the bolt ends depends on where it started, and the frontal arc reaches anywhere from 0 to 80px. Measured on the time-only version: a hit landed at 54px left the rabbit at **254px against a `deAggroRange` of 260** — six pixels of margin, and a hit at full reach would have pushed it past, so the rabbit would flee itself out of the fight, calm down and wander home at 12 HP. With the cap, a hit at 20px and a hit at 80px **both** end at 207px (the 80px case simply cuts the bolt from 850ms to 567ms) — deterministic, 53px inside `deAggroRange`.
  - **The latch (`hasPanicked`) is per rabbit, for its whole life.** Without it a rabbit under the threshold bolts on every hit, which is the version of this mechanic everyone has played and nobody likes. Verified: a second hit below the line produces no second bolt.
  - ⚠ **`onLoseAggro` must clear the panic phase, and the case that needs it is not the obvious one.** `canDeaggro()` is false during the beat, so the rabbit can't wander out of it — but the base's **`player.isDead` branch bypasses `canDeaggro` entirely**. Only `updateChase` ticks the panic timer, so without the reset a player dying mid-bolt would leave that rabbit frozen in the meadow permanently. Verified: killed mid-bolt, phase back to `none` immediately, patrolling normally 3s later.
  - **Animation is driven by the hop STATE, not by the velocity the base hands in** — the pause between hops zeroes that velocity, and reading it would flicker the sprite back to its idle frame twice a second. Verified over 240 frames of chase: `rabbit-run` throughout, 90 of them hop pauses, **0 idle frames**.

## Working conventions
- Only edit `public/assets/` to add/replace source PNGs, drop in Tiled maps, or update `README.md` — never leave scratch/debug images (crops, grid overlays) there; write those to a temp/scratchpad location and clean up after analysis.
- Keep balance numbers in `GameConfig.ts`, not scattered in entity code.
- When you discover a new hard-won fact about an asset's real pixel layout, add it to `public/assets/README.md` immediately — that file is what saves the next session from repeating the same pixel-archaeology.
