Every pixel-layout fact in there was measured directly from the PNGs (Python/PIL alpha-channel analysis), not guessed. Highlights, so you don't have to re-derive them:

- **`Teren.png` (640×395, surfaces) and `Nature.png` (640×230, props)** are both real 32×32 tile grids on a **33px pitch** (1px transparent gap between tiles), 19 columns each. Both are **regenerated** by `tools/build_tilesets.py`, so any hard-coded (col,row) pick into them is a coordinate with no owner — see the campfire below. Multi-tile props are stitched with `extractTileGrid()` — a deterministic block-copy, **not** alpha-scanning. A prior alpha-scanning approach (`extractCompact`) got fooled by a single stray opaque pixel from a decoration bleeding into a gap column and left a visible seam; don't bring that pattern back for these sheets.
- **A tile pick into a regenerated sheet fails silently.** The campfire used to be cut from Nature.png at pixel (132,198); rebuilding the sheet moved everything and that crop became part of a tree crown. The extraction still "worked". It is now always generated (`makeCampfirePlaceholder`), and the rule is: if code needs a tile from these sheets, give it a **named entry in the generator** first, not a coordinate.
- **Character.png** frames sit on a ~31×60 pitch (not a clean 32-grid) — explicit pixel offsets, not divide-by-count slicing. Column 4 of each direction row is the **attack pose**, excluded from the walk cycle. There's a separate small **sword icon** elsewhere on the sheet, extracted and attached to the player as a rotating child sprite during the attack pose.
- **Known art limitation: the left/right attack pose swaps hands.** Rows 2 (`left`) and 3 (`right`) of Character.png are pixel-for-pixel horizontal mirrors of each other (verified — diffing the attack frame of one against a flipped copy of the other shows near-zero difference in the arm/hand region). Mirroring an asymmetric figure swaps its handedness, so the arm that swings the weapon reads as the character's right hand when facing right and left hand when facing left, even though `ASSETS.character.handOffsets` documents all four as "the right hand" (that comment describes the code's *symmetric offset convention*, not a true anatomical guarantee). This is not a code bug — `Player.ts` never applies `flipX`; the mismatch is baked into the source PNG. A pixel-composite fix was attempted (pasting the `right` row's arm onto the `left` row's body) and rejected — at 31×60px it reads as visibly glued-on (arm at the wrong angle, a stray sleeve fragment, no shoulder attachment). Truly fixing this needs a hand-drawn "left-facing, right-hand cross-body swing" attack frame from a pixel artist, not a scripted edit. Leave the current mirrored art as-is until that exists.
- **rabbit.png** (96×72, generated by `tools/build_rabbit.py` — see `public/assets/README.md`) is a real directional sheet: idle down/up + a 4-frame hop cycle in profile (walk + run rows), reused mirrored via `setFlipX` for left/right instead of drawing both sides. Rabbit and Boar are the two enemies with an actual walk/run cycle (`updateAnimation`, driven by `Enemy`'s `updateAnimation` hook) rather than relying on the procedural motion FX alone — **but only for horizontal-ish movement**; movement dominated by the vertical axis still falls back to the static idle-down/idle-up frame, a deliberate scope cut matching every other enemy's baseline (not an oversight).
- **boar.png** (112×84, generated by `tools/build_dzik.py`, the sibling of `tools/build_rabbit.py` — see `public/assets/README.md`) is the second real directional sheet: same idle down/up + walk/run grid shape as `ASSETS.rabbit` (both slice through the one shared `sliceCreatureSheet()` in Assets.ts, and both animation sets are built by the one shared `createCreatureAnimations()` in Animations.ts), just a bigger frame (28×28) and a heavier quadruped trot instead of a hop. `Boar.updateAnimation` picks walk/run the same speed-threshold way as `Rabbit`, and never touches `setFlipX` while stationary — the charge's telegraph/recover phases already set their own facing and must not be snapped back by a momentary zero velocity.
- **wolf.png** (112×672, `tools/build_wilk.py`) and **greywolf.png** (128×768, `tools/build_szary.py`, the Szary's OWN sheet — see below) are the richest sheets yet: 6 states (Idle/Walk/Growl/Bite Attack/Hurt Reaction/Death) × 4 **independently drawn** directions each — the first creature sheets where left/right are NOT a mirrored runtime flip (rabbit/boar deliberately draw only 3 directions + `setFlipX`; the user wanted true 4-direction art here, so "left" is baked as a real mirrored frame inside each Python script instead). `Enemy` grew two new one-shot hooks for this: `onHurt()` (called from `takeDamage`, only on a hit that's survived) and `onDeathVisual()` (called at the top of `die()`, before the fade tween) — both default no-ops, reusable by the next creature with a sheet. `Wolf.playOneShot` plays growl on `howl()` (the pack alarm) and bite on `enterLunge()` — deliberately **not** before every lunge, which would add a telegraph the pack's dart is designed not to have (see the `lungeMs`/`lungeSpeed` comment in Wolf.ts); `GreyWolf` plays growl on `enterWindup` (his REAL telegraph — the whole reason this pays off for him specifically) and on `checkEnrage`, and bite on `resolveBite`. **Gotcha worth remembering if you touch this again:** the pre-existing `setFlipX` calls in `circleStep`/`enterLunge`/`patrol`/GreyWolf's `close` phase (written when every wolf-kind creature was one generic always-facing-right texture) had to be forced off (`this.setFlipX(false)` at the top of `Wolf.updateAnimation`) — left on, they'd mirror the already-correct 4-direction frames a second time, so a wolf moving left would show frames that read as facing right.
  - `Wolf`/`GreyWolf` share one animation implementation (`updateAnimation`/`onHurt`/`onDeathVisual`/`playOneShot`, all in `Wolf.ts`) that reads which sheet to use from `this.animFn`, a function assigned in the constructor **body** (`Wolf` defaults to `wolfAnim`, `GreyWolf`'s constructor passes `greyWolfAnim`) — not a class-field default, because a subclass's field initializers run AFTER `super()` returns, which would still be Wolf's default at the point the base constructor's own initial `this.play(...)` call runs. This is also what let GreyWolf inherit correct behavior for free the day he got his own sheet, with zero changes to those four methods.
- **neither spider nor the web shot has a PNG at all** — those textures are *always* generated procedurally (`makeSpiderPlaceholder` / `makeVenomSpiderPlaceholder` / `makeWebPlaceholder` in Assets.ts, driven by `ASSETS.spider` / `.venomSpider` / `.web`), so those blocks have no `key`/`path`. Drop e.g. an `assets/spider.png` in and wire a real extraction when art exists; same "always boots" guarantee either way.
  - **The skoczek is NOT the sieciarz at a different `scale`** — smaller frame (24×18 vs 28×22), earthy body with a venom-green abdomen, and a low wide leg stance instead of the sieciarz's hanging one. Same rule the Szary's own sheet exists for: two scales of one sprite read as perspective, not as two creatures. The sieciarz wears venom green only in its eyes (matching its web); the skoczek wears it on the body.
- **pig.png** (104×78, `tools/build_swinia.py`) exists in `public/assets/` but **nothing loads it** — no `ASSETS.pig`, no entity. It's art staged ahead of need for the village's livestock (`docs/swiat.md`), same move as the barn/cowshed/coop tiles in Buildings.png existing long before the village does. Wiring it in later is the same four-step recipe as the boar: `ASSETS.pig` (same shape as `ASSETS.rabbit`/`.boar`) + `sliceCreatureSheet`/placeholder in Assets.ts + `createPigAnimations` in Animations.ts + a new entity class.
  - The Szary is drawn from the wolf's shape language but **paler, heavier-browed and scarred, at a bigger `face` size** — deliberately not the wolf texture at a larger `scale`, because two scales of one sprite read as perspective rather than as two different creatures.
- **NPC.png** shares Character.png's exact pitch (same alpha-scan boundaries) — only the idle-down frame is extracted, since the merchant never walks.
- **items.png** is a true 32×32 grid with **zero gap** (unlike Nature.png's 33px pitch) — plain block-copy extraction, no separator math. Only a curated subset of the 20×30 sheet is wired up; the exact (col,row) picks (and how they were verified — don't eyeball the thumbnail) are in the README.
- **Buildings.png** (640×230) is a **modular kit** generated by `tools/build_budynki.py` — 88 tiles: log walls and **plank walls** (3×3 each), **two thatched roof shapes** (rectangular ridge roof + the gable `/\` set), an open-fronted bay + post, a rail fence, and doors/windows/chimney/barn-doors/dutch-door/hay-hatch/chicken-hatch/haystack/trough as **transparent overlays** placed on their own map layer. Buildings are assembled from a one-line description (`BUDYNKI_NA_MAPIE` in `tools/build_mapa.py`, mirrored by `WZORY` in the generator), not stamped as whole-building props — two earlier attempts did that and were rejected: baking a door into a wall tile means every door position is a new set of walls, and a finished 4×4 house cannot become a 5×3 one. Tile ids and sheet size live in `docs/budynki.json`. **Adding tiles must go in NEW ROWS** — the id is `row*19 + column`, so appending rows leaves every existing id untouched (verified: `forrest.tmj` renders the hunter's cabin identically after the sheet grew from 3 to 6 rows), while inserting a column would renumber the map into mosaic. Three things carry the look, each learned the hard way (details in `public/assets/README.md`): **a log is a cylinder, not a stripe** (8px full profile), **a corner log-end is a disc**, and **thatch needs courses whose boundary waves** — dead-straight courses read as corrugated cardboard, per-column random ones as speckled fur. **Every period divides 32** (log 8, course 8, stone 8, plank 8, diagonal course 16); that is the only reason the middle tiles repeat seamlessly, and test [4] checks it against the 90th percentile of internal differences, not the median. `b1.jpg`/`b2.png` are Gemini reference sheets — 98k colours, zero alpha, reference only, licence unresolved; `a1.jpg`/`a2.webp`/`a3.webp` are the same kind of material for the village (shape vocabulary only).
  - **The gable roof is a CHEVRON, not a filled triangle.** The first attempt built a solid pyramid from ridge to base — a front-on view of a hip roof — and it was rejected on sight. A real gable roof has **constant thickness**: the ridge runs along its upper edge, the eave along its lower edge, both diagonal and parallel, and **the gable wall shows between the arms** carrying the attic window. A filled triangle eats that wall and the building loses the storey that is its main feature in every reference.
  - Three consequences, all forced rather than chosen: **width under a `/\` roof must be EVEN** (the ridge sits on a tile boundary, so the 45° diagonals land exactly on tile corners — an odd width puts the apex mid-tile and every roof edge steps at each row boundary); **the roof is a layer ABOVE the wall** (`buildings-over`, and the chimney goes there too — put in the overlay layer it vanished under its own roof), so the wall starts at row `GRUBOSC_DACHU` and must be at least `szer/2 + 1` rows tall or an arm hangs over grass; and **thatch courses run parallel to the eave, i.e. diagonally**, on a 16px period because 16 divides 32.
  - **The whole village is thatched.** One iteration repainted the gable planes as timber planking, reading the reference sheets as a guide to the *material* — they are a guide to the **shape**. The only wooden part of this roof is the ridge beam at the apex.
  - **Both ends of the ridge beam were reported as cut off, and each needs a different fix.** Bottom: a **round log face** — flat-cut it reads as unfinished ("the ridge looks half made"), and the disc straddles a tile boundary so each half must be drawn from a **fractional** centre or it splits along the axis. Top: the beam **tapers toward the apex**, 2px at the peak widening to 10px eight rows down ("the ridge is abruptly cut at the end") — a flat start at a fixed height puts a horizontal cut across the peak, and no taper at all fills the whole wedge and reads as a mast.
  - **The thatch field is computed from GLOBAL position** (fixed wave phase, deterministic straw), so courses run unbroken across tile seams. That is also why the roof plane is **one tile with no variants**: there is no lattice to break, and adding a variant would introduce the seam rather than hide it. The visible symptom of getting this wrong was a rectangular patch of misaligned courses around the chimney, whose tile carries its own baked background.
  - **EVERY band drawn along a diagonal spills out of the tile that carries that diagonal — this is the load-bearing rule of the whole kit.** The diagonal runs corner to corner, so a band *w* px wide pokes a *w*-sided triangle into the two tiles touching its ends, and those tiles are ordinary planes that know nothing about it. Caught three times, each time only on an assembled building: the **eave shadow** (→ its own `podokap` tile row; without it the roof's lower edge was a staircase, measured at 22px of drop over 31px of width, jumping back 10px per tile), the **thick eave edge** (11px → `_naroznik_okapu` glued onto the plane above the eave, `*_okp`), and the **ridge roll** (4px → `_naroznik_kalenicy` on the plane under the ridge, `*_kal`). Consequence: **tiles within the band are not interchangeable** — the top row touches the ridge, the bottom row touches the eave, and each must carry a piece of the other band.
  - Roof band thickness is **at least 3 tiles (96px), not 2**, and the generator rejects a thinner single tile rather than quietly placing a wrong one — in a top-front view the roof is the building's main mass and must read as a surface, not as a frame around the gable. Wider buildings need MORE than 3 (see the `lico` note below), so actual building sizes are cottage 8×9 tiles, barn 10×11, cowshed 8×9, coop 6×7 (stays at 3 — narrow enough that `dodatkowe` is 0), stable 9×6 (ridge roof, not gable, unaffected). Related: the ridge beam's round end belongs to the **last** band row only; the version that reused one tile for every plane row drew two log faces on one beam — invisible at thickness 2, obvious at 3.
  - **The chimney has its background baked into BOTH of its tiles.** There is one layer, so a cell cannot belong to the roof and the chimney at once — a chimney tile replaces the roof tile rather than overlaying it. This bit twice: first the lower tile cut a gap in the ridge, then the upper tile punched a grass-coloured hole in the gable plane. An empty background is correct only where the chimney genuinely sticks out above the roof.
  - **Where the wall begins (`lico`) must scale with building WIDTH, not be the flat constant `GRUBOSC_DACHU` — and the fix has to ADD roof tiles, not just move the wall.** Each column starts its own local band at row `d` (further from the ridge = lower), so the edge column's band doesn't even begin until row `szer//2 - 1`. A fixed `lico = GRUBOSC_DACHU` let the wall start before that column's roof had rendered a single fully-opaque tile — its corner log-end (the same disc-shaped "zamek" that marks every bale-wall corner) then sat exposed on bare grass, past the roof's edge entirely ("beams sticking out"; invisible at 6-wide, worse the wider the building gets). **The first fix attempt just pushed `lico` down to `max(GRUBOSC_DACHU, szer//2)` without extending the roof itself — which opened a *different* hole**: the ridge-adjacent columns had already finished their (unchanged) 3-row band by the old `GRUBOSC_DACHU`, so the gap between where their roof now ended and where the wall newly began showed bare grass right in the gable notch. Reported immediately: "you moved a row of tiles instead of adding a row of tiles, now we have a hole." The correct fix inserts `dodatkowe = max(0, szer//2 - GRUBOSC_DACHU)` extra, fully-opaque plain-thatch tiles into **every** column's band (not just the wide ones) before the eave, so the roof genuinely grows deeper for all columns together and the wall start moves down by exactly the same amount the roof grew. Two follow-on details, each caught by test [10], not by eye: the eave's baked-in thick-edge overlay (on the tile named `*_dol`/`*_okp`) is only correct on the tile *immediately* before the true eave, so it has to move to `r0 + lico - 1` rather than staying fixed at `r0 + 2`; and the ridge beam needs its own plain "still going, no cap yet" filler tile (`szczyt_fill`) for the inserted rows, or the beam visibly breaks in the middle before resuming at its round end. Kept identical across `_dach_szczytowy` in both `build_budynki.py` and `build_mapa.py`, and `build_mapa.py`'s standalone `wysokosc_budynku` estimate — all three must agree, since the wall-start row is exactly their shared seam. Test [11] composes a real building (roof and wall together, not just the roof) and checks every column for any transparent pixel between its first opaque roof pixel and the foundation — the only test that would have caught either version of this bug, since [8]-[10] only ever look at the roof in isolation.
  - Verification test [8] composes the whole roof and checks the band has no holes inside and nothing outside it — an off-by-one in a diagonal mask shows up as a grass-coloured seam down an entire arm, and that is invisible on a single tile. Test [9] catches the staircase specifically: on a 45° edge the sum (column + lowest opaque row) is constant, so its spread *is* the step height in pixels. **Test [10] is the one that matters most**: it compares every pixel of the band against a globally-computed reference (`_wzor_pasa`), which is the only way the interior spills show up at all — [8] and [9] look at the silhouette and both stay green while a band is broken (verified: disabling the eave corner leaves [9] at OK and [10] at 234 bad pixels).
- **Indoor.png** is still reserved for future interiors and has **not** been pixel-analyzed — don't assume it shares that pitch without re-verifying.
- If a PNG is missing, the game generates a colored placeholder and logs which file to add — it never fails to boot.
